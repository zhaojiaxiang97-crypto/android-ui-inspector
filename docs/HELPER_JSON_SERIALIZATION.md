# 大截图 JSON 输出优化（D3）

更新：2026-10-17。代码、真机固定数据对照及完整业务回归已完成，新版 Helper 已安装。固定数据的常见图片档 JSON 编码中位耗时下降 73%–77%；完整任务仍约 66 秒，尚未达到阶段 D 的整段提速验收。

## 目标

[D2](AUTOMATION_TIMING_DETAIL.md)完整流程的 23 次采集中，JSON 序列化累计耗时 7.685 秒。此次只优化快照响应中的大段图片字符串，不修改采集范围、控件树、无损 PNG、授权、输入和验收条件。

## 实现约束

- 原 JSON 对象及嵌套数据保持不变，其他字段继续使用 Android 原序列化器。
- 仅对合法且有界的 Base64 使用批量追加。非适用数据在序列化前选择原路径，不修复输入，不吞掉错误后重做。
- 允许 JSON 字段顺序和可选斜杠转义变化；解析后所有字段、类型和 PNG 字节必须一致。
- 校验、复制、缓冲分配及拼装全部计入 JSON 阶段；最终仅做一次 UTF-8 转换，HTTP 长度来自实际字节。

最终实现只接入快照响应：要求普通 JSONObject、成功响应、PNG 截图标记和合法 Base64；复制其余字段后由原序列化器处理，再预分配缓冲批量追加图片字段。Base64 使用 128 字节查表，所有 65,536 个字符的映射均与原分支写法穷举比对；padding 未用位和 24 MiB 字符上限仍检查。JSONObject 子类、无图、失败、非法或超限数据继续走原路径。

## 验证分层

1. 语义回归：Unicode、转义、Base64 填充与非法值、无图与失败响应、上限、原对象不变、异常及 HTTP 长度。
2. 同机固定数据：手机上直接调用真实 Android JSON 实现与生产候选，以同一对象交替 AB/BA 编码；冷首对、预热及正式样本分开记录。
3. 完整业务回归：继续使用现有“返回 → 我 → 收藏 → 严格末端 → 最后有效视频 → 播放状态确认”流程，保留全部冻结证据。

固定数据基准用于判断编码开销；动态业务单轮只用于功能验证和观察，不代替[阶段 D](AUTOMATION_NEXT_STEPS.md)要求的前后各 10 轮完整流程验收，也不能用来宣称整体提速 20%。

## 结果

### 同日原版流程

升级前沿用 D2 Helper 运行一次完整业务，1/1 通过：墙钟 66.361 秒、产品 60.456 秒，6 次确认输入、0 次未知输入，证据完整。23 次实际请求的 JSON 序列化累计 6.481 秒、UTF-8 累计 0.234 秒；8 份冻结归档、10 个唯一步骤和 19 个保留观察均已通过离线汇总校验。失败现场的 3 个未产出观察槽位仍明确保留，未视为附件缺失放行。

这是同日功能与计时参考，视频内容和恢复次数会变化，不能单独作为受控性能基线。私有记录位于主工作树 `.benchmarks/stage-c/d3-baseline-pilot/`，调试授权已在本轮结束后停止。

### 压力测试记录

首次固定数据测试中，small、medium、large 三档的 AB／BA 共 6 个进程均完成。near 档首个进程在输出样本元数据后被系统终止（退出码 137，未产生第一对结果）；它不能计入通过或收益样本，也不能据此断言是候选编码器失败。

核查发现测试程序同时保留了多份大对象。缩短生存期后，1024 MiB 和 512 MiB 进程上限下仍各被终止一次；新增阶段记录表明两种编码均已完成，终止发生在原版输出的验证阶段。三次退出记录均保留，不能直接认定为 Java OOM 或生产编码失败。

最终改用 Android `JsonReader` 从 UTF-8 字节流逐项校验，避免整份 UTF-16 输入字符串和第二棵 JSON 树；仍严格核对所有字段、类型、Unicode、PNG 字节及首对像素，并拒绝重复／缺失／未知字段和尾随内容。固定数据、生产代码和计时边界未改变，没有强制 GC。最终 near 档 AB／BA 均完整通过。

### 真机固定数据结果

同一台 Android 14 手机、平台自带 `org.json`，最终统一使用 `app_process -Xmx512m`。四档数据各用 AB／BA 两个独立进程；每进程分别记录首对、2 对预热、6 对正式样本和单独的内存采样。正式时间样本不启用内存采样线程。每档下表为 **12 对预热后样本的中位数**，单位为毫秒。

| 合成 PNG 大小 | JSON 原版 → 新版 | JSON 耗时下降 | UTF-8 原版 → 新版 | JSON + UTF-8 原版 → 新版 |
| --- | ---: | ---: | ---: | ---: |
| 1.15 MB | 38.008 → 8.803 | 76.8% | 4.068 → 4.054 | 42.048 → 12.798 |
| 2.41 MB | 80.031 → 21.588 | 73.0% | 9.092 → 8.829 | 89.266 → 30.349 |
| 3.42 MB | 113.600 → 29.275 | 74.2% | 12.780 → 12.414 | 126.686 → 42.772 |
| 13.83 MB，近上限压力响应 | 718.226 → 546.592 | 23.9% | 88.262 → 105.834 | 808.632 → 648.332 |

合计列先对每个样本相加再求中位数，没有把两列中位数直接相加。near 响应另外包含合成 XML 填充，接近 32 MiB；它是编码压力测试，不是产品完整快照协议的接受测试。该档 UTF-8 反而更慢，合计中位数仍减少约 160.3 毫秒，未隐去这一结果。

另用相同流式验证程序、相同数据和 512 MiB 上限，对最初多分支校验版做中／大档 AB／BA 对照。候选 JSON 耗时除以同对原版耗时后，中位比例由约 0.616／0.606 降至查表版的 0.267／0.264，因此保留查表实现。早期不同验证程序或内存上限的记录没有混入最终统计。

独立审计核对了最终 12 个进程、120 对样本、72 对正式样本和 12 对独立内存采样，所有结束标记、顺序、字段相等声明及固定输出／PNG 摘要通过，汇总值与逐行重算一致。真实 Android 自检的 5 项回退与 9 项流式校验（1 个正例、8 个反例）也通过。首对单列保留，不与预热后样本合并；这些样本不用于承诺稳定 P95。

该结果只证明固定数据的编码收益，未证明完整任务提速。原业务截图约 1.28–3.74 MB，前三档覆盖其常见大小；合成内容与真实页面仍有差别。内存采样只表示观察到的 Java／native 分配高水位，不是精确峰值或进程 RSS；512 MiB 的独立测试进程也不代表 Helper 在相同内存条件下运行。

私有数据：主工作树 `.benchmarks/json-d3-final-lut/`（最终八进程与汇总）、`.benchmarks/json-d3-streaming-branch/`（原分支版对照）。首次与后续验证阶段退出的记录分别保留在 `json-d3-device`、`json-d3-branch-bounded`、`json-d3-branch-512` 目录。

### 新版完整业务与工程检查

同一设备、同一 Debug App，使用原计划完成“返回 → 我 → 收藏 → 严格末端 → 最后有效视频 → 播放状态确认”，**1/1 通过**。6 次确认输入、0 次未知输入，8 份冻结归档、10 个唯一步骤、19 个保留快照；证据完整。独立审查核对全部 42 个附件（21 树、21 图）的摘要、字节长度、树解析、PNG 完整解码和正式离线导入，均通过。2 次滚动后以双帧确认结束标记；末卡唯一匹配，仅点击一次；原失败及 3 个未产出观察槽位保留，同请求恢复未补发点击。播放确认仍是业务语义和新双帧校验，不代表已测试解码质量或实际播放进度。
