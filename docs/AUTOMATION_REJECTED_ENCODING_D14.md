# D14：拒绝观察的图片编码优化候选

更新：2026-10-18。状态：实现、本地验证和真机试跑完成；真机门槛未通过，未合入，原 Helper 已恢复。

## 本轮结论

已实现“观察已确定不完整时跳过 PNG、Base64 和图片传输”的受限候选。本地测试证明该分支不执行编码、不会提供可操作快照，完整观察仍执行原流程。

真机试跑在返回后的响应等待阶段超时，未验证到这条新分支。按事先记录的门槛，没有进行三轮扩展，也没有整合生产源码。原目录保留 D11，手机恢复为测试前完全相同的 Helper 安装包；两次恢复后只读采集成功。

本轮没有新的整段提速结论。D12 的 5.83% 整段结果和 20% 目标未达到的状态不变。

## 查到了什么

原 Helper 在树遍历结束后截图，随后检查显示器、窗口和焦点。即使已记录子节点缺失、窗口变化或几何异常，仍会继续生成 XML、PNG 和 Base64，最终才返回不完整观察。

现有短时条件等待也不能直接代替导航就绪判断：`waitDebugAppCondition` 调用 Helper 前后都会核对前台和焦点，焦点空档时在入口就会失败。它是控件条件提示，没有解决窗口切换空档；本轮没有加入固定等待或扩大重试预算。

## 独立候选的改动

工作树：`rejected-observation-encoding`，从当前源码共同快照 `8b6aa62e6bc407ee1bafcd94889563c609ca61b5` 开始，没有带入 D13 未合入的 Activity 错误分类候选。

- Java 模板在已有截图和窗口检查完成后，如果观察已失败，返回固定的 `failureStage=before-image-encoding` 诊断响应，跳过 XML 输出、PNG 编码和 Base64。
- 此响应明确为 `success=false`、`has_screenshot=false`，不包含树或图片；输入绑定已清除，不能用于后续输入。
- 桌面仅接受严格匹配的新失败结构。通过原有显示器、窗口清单、服务身份、采集时序和诊断原因校验后，最多提供一个“可尝试原有有界恢复”的失败元数据对象。
- 后端与会话校验、原重试次数和期限、最终新双帧要求均保持原规则。未知字段、错误阶段、异常尺寸、截断、其他 App 或无效时序不会获得恢复资格。
- 成功响应的结构和解码校验保持原样。旧 Helper 的原有失败响应也继续被原逻辑处理；旧桌面遇到新失败结构会安全拒绝，不能把它当完整观察。

这版仍会执行截图和窗口检查。它优化的是已知失败后的编码与传输，不宣称已跳过截图，也不伪造零时长编码计时；跳过阶段没有对应计时字段。

- 执行生产 Java 方法的故障夹具确认：完整观察恰好编码一次；已知树失败时编码调用为零，没有 XML、图片或输入绑定，未执行的编码异常不会被伪造为失败原因。
- HTTP 和会话测试覆盖新失败结构、完整观察兼容、身份变化、旧采集时间、未知字段、错误图片标志与诊断，传输本身不自动重试。

首次本地命令误用了不存在的 JDK 路径，改用现有 JDK 后通过；原失败日志保留。这不是生产代码测试失败。
