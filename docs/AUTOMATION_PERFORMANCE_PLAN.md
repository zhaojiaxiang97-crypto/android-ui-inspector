## 2. 实测基线

### 2.1 场景

2026-10-15 真机回测：退出当前视频 → 进入“我” → 打开收藏 → 滚动到最后一个可播放作品 → 播放并验证。

实际发生：

- 进入“我”后，收藏已经处于选中状态。
- 发送 5 次输入：返回、进入“我”、两次滚动、打开末项。
- 列表显示 13 条收藏，底部提示 1 条失效，可播放封面共 12 个。
- 最后点击已成功发送，但采集遇到“焦点窗口为空”；补充只读观察后确认视频播放。
- 本次结果只能证明这一个设备和场景，不代表全部页面的成功率。

完整原始证据保留在本机应用数据目录；本地回测记录为 `.benchmarks/favorites-retest-20261015-2323.md`。该目录中的业务截图和原始日志不作为公共仓库文档附件。

### 2.2 三种耗时要分开

| 指标 | 实测 | 解释 |
| --- | ---: | --- |
| 输入命令执行累计 | 1.909 秒 | 3 次点击、2 次滑动，包括输入进程开销 |
| 应用步骤累计 | 128.576 秒 | 包含输入、采集、校验、恢复等；已经包含上一行 |
| 完整回测经过时间 | 547.961 秒 | 从首次采集到最后观察完成；已经包含应用步骤 |
| 应用步骤之外的时间 | 419.385 秒 | 两者之差；含模型判断、图像查看、工具往返、上下文恢复等，尚未逐项测量 |

不能将这几行相加，也不能把 419.385 秒全部归因于手机、网络或模型推理。

其他直接证据：

- 7 次显式采集累计 43.150 秒，单次约 4.9—7.4 秒。
- 4 次“操作前重新采集”累计 27.241 秒，是减少重复工作的候选开销，不能承诺全部省掉。
- 包含前后采集的点击/滚动约 15—16 秒。
- 两次快照过期拒绝本身仅耗时 13 毫秒；真正成本是后续恢复调用。
- 一次首次滚动因几何重叠要求视觉确认，确认后成功。
- 整体历时受人工式逐步观察及上下文恢复影响，不能直接作为新版本稳定性能基线。

### 2.3 当前典型调用流程

```text
外部采集 → 查询目标 → 查看证据 → 发起动作
    动作内部：重新采集 → 校验目标 → 输入前检查 → 发送一次输入 → 再次观察
外部继续查询或重新采集 → 判断是否完成
```

优化重点是合并外部流程、复用返回结果，以及降低内部观察成本。

## 4. P0：分段计时已实现，完整场景基线待补

### 4.1 分段计时

给每个动作和采集分配关联 ID，记录单调时钟耗时和可供回放的时间戳：

| 层级 | 至少记录 |
| --- | --- |
| 调用入口 | 请求进入、排队开始/结束、返回结果 |
| 观察 | 目标检查前、读树、截图、几何检查、目标检查后、解析、保存 |
| 设备命令 | 命令类别、启动/结束、结果、次数；不记录令牌和敏感输入 |
| 操作 | 重新定位、语义/几何/遮挡校验、输入开始/结束、动作后恢复 |
| 返回 | 序列化、必要证据落盘、可选附件处理 |
| 外层运行器 | 调用间隔、工具调用次数、截图查看次数；能测到的模型等待单独列出 |

并行的树读取和截图按各自区间记录；展示关键路径，不能简单相加当总耗时。保留失败和取消步骤，不能只统计成功样本。

当前源码在返回值及 `step.timings` 中保存关联 UUID、开始时间、单调时钟总耗时，以及阶段的父区间、相对开始时间、耗时和成功/失败/取消状态。已接入观察前后目标检查、树、截图、几何、解析、清理、重新定位、输入校验、输入、验证与保存；设备命令只记录固定类别、区间、结果和次数，不记录参数、令牌或输出正文。观察标注显式、操作前、操作后、恢复、验证等原因。

报告展示各阶段起止区间与总经过时间，保留重叠关系；单步最多保存 2048 个区间，超过时记录省略数，命令及观察次数仍累计。旧报告没有 `timings` 时显示“未记录”。最终计时元数据回填自身不计时，避免保存自身计时造成递归。跨请求的 Agent 判断、工具往返和截图查看不在单步计时内；外层运行器的这些指标尚未采集，不能按 0 处理。会话仍拒绝并发动作，没有把未执行的排队时间记成设备耗时。

报告中区分：

- 实际输入次数；
- 观察次数及触发原因：显式、动作前、动作后、恢复、验证；
- 工具调用次数与模型决策轮数；
- 当前设备、采集后端、页面场景和冷热状态。

### 4.2 基线与验收

- 用固定离线场景验证阶段计时是否完整、顺序是否正确。
- 真机固定设备、App、网络及初始页面；基线和改造版交替运行，减少环境波动。
- 冷启动单列；每个代表场景至少 10 次热运行，报告中位数和最大值。需要 P95 时增加到至少 30 次，并注明样本量。
- 页面内容、收藏数量或网络状态变化时标注，不能合并为同条件对照。
- 对照版本使用相同验收强度；连续两次观察与人工单次查看不能混为同一种验证成本。
- 验证新增埋点不改变输入次数、结果或取消行为。

已交付分段计时字段、报告展示/导出及离线基线脚本。运行 `bun scripts/automation-offline-baseline.ts 10` 可重复检查固定模拟观察的成功、顺序截图、读树失败和取消场景；每场景至少 10 个样本，输出中位数、最大值及阶段区间，样本数达到 30 才输出 P95。设备依赖全部模拟，这些结果用于检查计时和时序，不代表手机耗时。真机基线仍按本节条件另行采集，P0 不承诺明显提速。

## 5. P1：复合单步、刷新定位和观察恢复已实现

### 5.1 新增“定位 → 操作 → 等待条件”的单个入口

已实现 `perform_ui_step`。参数与 [共享协议](../shared/debug-protocol.ts) 一致；下例中的会话 ID、请求 ID 和控件条件需替换为本次实际值：

```json
{
  "sessionId": "00000000-0000-4000-8000-000000000001",
  "requestId": "00000000-0000-4000-8000-000000000002",
  "target": {
    "selector": { "contentDesc": "我" },
    "clickable": true
  },
  "action": { "kind": "tap" },
  "expect": {
    "selector": { "text": "收藏" },
    "state": "visible"
  },
  "timeoutMs": 20000
}
```

目标约束与验收条件必须按实际控件填写；“收藏”只是接口示例。`target.within` 可用精确 selector 限定一个唯一匹配的子树范围；`clickable`、`scrollable` 是 `target` 下的可选筛选字段。目标和范围均必须唯一，没有 `expectedMatchCount` 参数。`action.kind` 为 `tap / scroll / back`；`scroll` 另含 `direction`，可选 `distance / durationMs`；`back` 不传 `target` 或视觉确认。`target.target` 默认为 `self`，点击可显式指定 `clickable-parent`。

`expect` 可省略；存在时支持精确 selector 及 `visible / absent / enabled / disabled`。`perform_ui_step.timeoutMs` 默认 45000，范围 1000–60000；`resume_ui_step.timeoutMs` 默认 30000，范围相同。动作和后续验证共享本次预算，且仍受会话到期与取消约束。

执行流程：

1. 验证会话授权、设备、目标包、剩余时间及请求去重状态。
2. 取得本次新观察，在明确窗口/父级范围内匹配 selector。
3. 必须唯一匹配；0 个返回未找到，多个返回歧义，不随意选第一个。
4. 执行现有目标稳定性、可输入范围、遮挡及几何检查。
5. 只发送一次输入。
6. 用动作后观察作为预期条件的第一次候选确认；仍须连续两次观察符合，尚未满足时在预算内继续观察。
7. 一次返回结果、当前 snapshotId、目标摘要、耗时和必要证据。

关键边界：

- selector 各字段保持精确匹配，并限制授权 App、目标窗口、可见和启用状态；未知可见性仍走现有检查。
- 文字节点不可点击时，不自动猜测父控件；需要调用方显式选择 clickable-parent，再执行父级范围及命中校验。
- 新 selector 路径的首次新采集直接作为动作前依据，避免先采集定位、又无条件执行第二次完整动作前采集；输入前即时身份/几何检查仍保留。
- 等待条件保持现有连续两次观察确认要求：动作后的新观察可计为第一次，再采集确认第二次；操作前快照不能计入。这样减少重复采集，同时保留验收强度。
- 需要对比既有截图或目标身份时，保留相应复核，不能把所有场景强行合并。
- 验收条件只支持受限、结构化谓词，不执行页面提供的代码或指令。
- 无法明确判断遮挡时，返回 `recovery.kind=visual_confirmation_required` 和对应截图；该状态下不发送输入。补充视觉确认会改变参数，仅在原请求明确 `not_sent` 时使用新请求 ID。
- MCP 尽量随结果返回简短摘要和必要图像，减少“导出截图 → 再打开图片”的额外调用。
- CLI 和 MCP 使用同一执行器，不能分别维护两套定位逻辑。
- 单步预算由请求、会话剩余时间与服务器上限共同约束；内部采集/等待不能各自重新获得一份完整预算。

### 5.2 过期时刷新并重新定位

保留旧 `snapshotId + nodeId` 接口的现有行为，新入口通过 selector 重新定位：

- 快照过期时，旧节点只能作为参考身份，不能直接使用旧坐标。
- 重新采集后，结合资源 ID、类名、文字/描述、父级范围和窗口匹配。
- 未提供足够身份条件、出现多个相似节点、目标切换页面时停止并返回新候选。
- 不能依赖树路径不变；节点 ID 可能每次都改变。
- 旧视觉确认绑定原快照、目标和区域，不能自动继承到内容已变化的新截图。
- 返回当前 `snapshotId` 与操作目标摘要，重新定位区间保存在 `timings` 中。当前新入口每次先读新快照，不复用过期坐标；没有额外的“自动跳过已选中控件”规则。

此项解决的是过期恢复需要多轮工具调用的问题，不是简单把 30 秒改为更长。

### 5.3 补齐 null-focus 恢复

动作后恢复现已识别 `FocusUnavailableError` 的 `null-focus`，与窗口切换及暂缺有效控件树一起进行有限重试。操作前暂时无焦点仍会阻断输入。

实现边界：

- 通过明确错误码/类型分类，将动作后的短暂 `null-focus` 纳入观察恢复；初版保留现有最多 3 次与 250 毫秒间隔，同时受总预算约束。
- 外部 App、窗口歧义、断线、授权撤销等仍按各自原因停止。
- 按有上限的时间预算观察，不以增加固定长等待作为主要手段。
- 恢复过程中显示“输入已发送，正在确认页面”，不将其描述为未点击。
- 预算耗尽时返回“输入已发送、结果尚未确认”。
- 后续恢复调用只继续观察，不重新发送原动作。

### 5.4 请求去重和恢复结果

新复合入口使用 UUID 格式的 `requestId`，处理调用方超时后的重复请求：

- 同会话、同 ID、同参数：返回执行中状态或已保存结果。
- 同 ID、不同参数：拒绝，避免误把新动作当旧请求。
- 输入处于 `sent` 或 `unknown` 时：只允许查状态/继续观察。
- 进程重启后，无法证明是否发送的请求标记为未知，不自动恢复发送。
- 最小请求与发送状态需要可靠保留；只有大图等可选附件可以异步处理。
- 去重保留期限至少覆盖会话及合理的恢复窗口，设置容量边界。

`get_ui_step({sessionId, requestId})` 只查询已存状态和结果，不采集、不输入，也不增加调试步骤。`resume_ui_step({sessionId, requestId, timeoutMs})` 仅对原发送状态为 `sent / unknown` 的请求继续观察，使用原 `expect`，不会改写原动作或重新发送输入。更改 selector、预期、超时或视觉确认均属于改参，同一个 ID 会拒绝；确实未发送且需要修正条件时，使用新 ID。

本地 `requests.json` 独立保存请求、发送状态与结果，单会话最多 1000 个请求、16 MiB，容量满时拒绝新请求，不为接收新动作删除旧去重记录。重读未结束记录时标为 `interrupted`，可能已经派发的状态保守记为 `unknown`；程序重启不会自动恢复授权或输入。

### 5.5 返回状态

当前返回将 `dispatchState`、`requestState` 与 `verified` 分开。`requestState=running / completed / interrupted` 表示请求执行和保存状态；`completed` 不等于任务通过。尚未找到请求时，查询返回 `found:false`。

| 输入状态 | 当前结果含义 | 上层行为 |
| --- | --- | --- |
| not_sent | 定位缺失、歧义或需要视觉确认；`verified:false` | 补充证据或调整目标 |
| sent | `requestState:running` | 等待或查询同一请求 |
| sent | `verified:true`，连续两次条件符合 | 进入下一步；整体任务仍按固定任务规则验收 |
| sent | 未提供预期或条件尚未确认；`verified:false` | 查看证据，必要时只恢复观察 |
| unknown | 无法确认原输入结果；后续观察可独立确认页面条件 | 停止输入，只读确认，不改写原发送回执 |

没有预期条件时，最多说明动作已经发送，不能返回任务通过。

## 6. P2：有边界的连续滚动已实现

### 6.1 接口与控制范围

已新增 `scroll_until`，CLI 为 `scroll-until`。参数包含：

- 滚动容器 selector、父级/窗口范围；
- 内容方向；
- 目标条件或终点证据；
- 最大滚动次数、总超时；
- 请求标识及取消能力。

默认最多 6 次、服务端硬上限 12 次，总预算默认且最多 120 秒，并受会话剩余时间限制。每个手势后的新观察直接作为下一次定位依据，避免无条件重复采集；输入前即时检查仍执行。

`target.selector / within` 必须唯一定位启用的滚动容器。`until.selector` 在容器可见范围内唯一匹配，`kind=target / end_marker` 区分目标与明确终点。可选 `loading / empty` 也是容器内的精确条件。初始条件已满足时仍读取两次确认，零次输入返回；空列表也确认两次，但返回 `empty`、`verified=false`。加载期间只观察，容器消失则停止。

内置 CLI 请求等待 135 秒、桌面桥接 130 秒，覆盖执行预算。外部 MCP 客户端需把请求等待设置为至少 135 秒；部分客户端默认 60 秒，会提前取消。取消只停止后续工作，不能撤回已发送的滑动。

每一步仍执行：

```text
新观察 → 唯一定位容器 → 计算可见输入区域 → 校验遮挡
→ 发送一次滚动 → 观察 → 检查进度/终点 → 继续或返回
```

避免底部导航、嵌套滚动冲突和跨窗口输入，复用现有滚动几何及视觉确认逻辑。

### 6.2 进度与终点证据

当前根据容器内唯一的语义条目与相对位置判断进展，不使用节点路径或复用的 nodeId。重复文字、无文字图片列表等证据不充分时标记 `unknown`；两次可靠无变化返回 `no_progress`，不声明到底。可靠总数、末项索引和后端滚动事件尚未接入，不能当作当前已支持的终点证据。

终点按证据区分：

| 证据 | 处理 |
| --- | --- |
| 明确“没有更多”等底部标识 | 验证属于目标列表、可见且不只是后台节点 |
| 可靠条目总数及末项索引 | 后续能力；当前未接入，不推测末项 |
| 后端可靠的不能继续滚动结果 | 后续能力；当前未接入 |
| 连续无位移、相似截图 | 仅记为无进展，不能直接宣布已到底 |
| 加载中、网络慢 | 预算内等待；超时返回未确认 |
| 达到次数/时间上限 | 返回预算耗尽及当前进度，不声明完成 |

“最后一个可播放作品”与“总数里的最后一条”分开表达。失效条目不自动清理。

### 6.3 视觉确认如何处理

- 遮挡证据不足时，中断任务并返回当前截图、目标和走廊。
- 确认只适用于被查看的快照和区域，后续截图变化后不能无限沿用。
- 本轮只允许首个手势使用传入的视觉确认；后续仍独立校验，遇到遮挡证据不足立即停止。
- UIAutomator 无法证明隐藏侧栏不可交互时，仍可能需要多次视觉确认；P2 不承诺在所有页面完全无人介入。
- P3 获得更完整的可见性/窗口证据后，才进一步减少此类中断。

### 6.4 P2 验收

已覆盖两次滚动到明确终点、起始已满足、瞬时提示、加载/空列表、重复条目、无语义条目、无进展、次数/时间上限、窗口与方向变化、嵌套容器、视觉确认、取消和不确定输入。失效条目的业务含义由调用方明确条件表达，当前不自动寻找或播放“最后一个有效视频”。

固定离线场景中，两次滑动共 4 次观察（初次、两次动作后、终点复核），只发送 2 次输入。起始已满足为 2 次观察、0 次输入。此处只验证调用数量，不代表真机秒数或提速比例。

每个内部手势保留前后 snapshotId、实际输入轨迹、发送回执、耗时与进展判断。台账在派发前持久化 `unknown`，不能删除或改写既有手势；一个请求内后续未发送的手势不会抹掉先前输入。中间操作快照及两次确认快照受现有证据容量上限管理；裁剪丢失确认树时，报告保留记录并降级为未验证。

同 ID 同参数只返回原状态；`get_ui_step` 查询进度，`resume_ui_step` 只继续观察原条件，不发送任何手势，零输入的滚动任务也可只读重验。恢复保留原请求的未知发送状态。需要继续滚动时，在查清已有请求状态后，以新请求从当前页面继续；不会自动从头重放，也不会在结果未知时自动开启下一批。

## 7. P3：可选 Helper 已接通自动操作

### 7.1 为什么值得做

当前每次 UIAutomator 观察都会执行新的 dump；正常路径还会启动约 12—14 次 ADB 子进程，包括前后目标检查、树读取和截图。调用数量已从源码确认，具体耗时占比仍需 P0 测量。

本轮之前的 Helper 已能读树，但：

- 仍只支持只读观察，输入前会拒绝 Helper 快照。
- 每次读取建立、检查并清理自有转发。
- 树读取后再进行主机侧截图，没有贯通组合采集路径。

因此，单纯在外层使用 Helper 采一次，再切回 UIAutomator 操作，可能反而增加总耗时。

### 7.2 借鉴 ARTEMIS 的范围

参考固定版本 `google/artemis@351ca8422f7b5b54e80a9c1ce03a222e02415b6b`：

- [无障碍服务及 HTTP 生命周期](https://github.com/google/artemis/blob/351ca8422f7b5b54e80a9c1ce03a222e02415b6b/packages/artemis-accessibility-helper/app/src/main/java/com/artemis/helper/ArtemisAccessibilityService.java)：使用设备端服务提供观察入口。
- [组合读取树与截图](https://github.com/google/artemis/blob/351ca8422f7b5b54e80a9c1ce03a222e02415b6b/packages/artemis-accessibility-helper/app/src/main/java/com/artemis/helper/HierarchyDumper.java#L237-L290)：并发获取并打包返回，减少分散往返。
- [按需字段](https://github.com/google/artemis/blob/351ca8422f7b5b54e80a9c1ce03a222e02415b6b/packages/artemis-accessibility-helper/app/src/main/java/com/artemis/helper/HierarchyDumper.java#L54-L91)：只返回本次需要的数据。

其方法名中的 atomic 不等于 Android 保证树与截图严格同帧。我们仍需记录各自时间、窗口和几何信息，并检测采集中页面变化。

### 7.3 本轮实现

1. `helper-session.ts` 按桌面授权会话延迟创建并复用自有转发，绑定设备、ADB、令牌、目标包和服务实例。每次读前后核对转发归属；取消、失败和会话结束清理，退出会等待清理完成。
2. 设备端提供认证后的 `/inspector/capabilities` 和 `/inspector/snapshot` v1 接口。要求 Android 11 以上、完整字段、窗口清单、可见区域及 PNG；旧版能力不足直接说明原因，不自动安装、配对或切源。
3. 同一请求先读完整诊断树，再拍无损 PNG。`helperObservation` 保存服务/采集 UUID、单调时钟、前后显示器与窗口清单。桌面继续独立检查 ADB 前台窗口和屏幕尺寸。
4. `perform_ui_step` / `scroll_until` 接受 `backend: "accessibility-helper"`；旧单步入口基于有效 Helper 快照继续同源重定位，`wait_for_ui` 和固定任务验收也使用同源的新观察。默认值仍为 `uiautomator`。
5. 输入仍走原 ADB 受控执行器。Accessibility 窗口 ID 与 ADB 窗口标识分别核验；普通点击/返回允许正常页面跳转，连续滚动仍固定原窗口和几何范围。
6. 请求台账在首个输入之前保存 Helper 来源，恢复沿用原后端，只继续观察；服务重启、旧 captureId、时间倒退和跨源视觉确认均拒绝。旧请求未写 backend 时仍按 UIAutomator 默认值去重。
7. 报告保留来源和可见性证据，导入复核服务、窗口及确认顺序；缺证据不标记成功。需要回退时由调用方显式重新采集 UIAutomator 并重新定位，不复用旧节点或坐标；当前自动回退次数为 0。

Helper 是设备端工具，不要求目标业务 App 集成 SDK。安装、启用和配对沿用现有显式配置流程，不在每次自动任务中重新执行。

生成脚本仍校验固定上游源码摘要，新增协议实现保存在 `scripts/helper-templates/InspectorObservation.java`，与上游旧接口分开。源码、生成摘要和 Android 构建已经验证。初次接入批次未安装；后续带细分计时的 APK 已更新并完成本节记录的真机采样，桌面安装候选版本边界见验收清单。

### 7.4 图片与可见性边界

- 给模型查看的预览图可以压缩；坐标必须绑定原图尺寸和变换。
- 当前严格像素确认不能直接使用 JPEG 重新编码后的差异当作控件变化。
- 需要精确像素验证时，保留无损截图或无损区域证据；不能把两个阶段的图像随意混用。
- 不可见节点保留在诊断树中；只有显式可见、字段完整且处于有效裁剪范围内的控件参与输入。缺失可见性不会按可见处理。
- 当前裁剪证据覆盖屏幕、窗口和滚动祖先；无障碍 API 不能证明任意 ViewGroup 的裁剪或像素遮挡。覆盖窗口、未知窗口类型和冲突控件仍保守拒绝，不靠删除空节点放行。
- 树与 PNG 按先后顺序采集，不承诺同帧。动态视频仍可能让严格像素确认失败，需要新证据。

已加入窗口后检、PNG、Base64 及主机响应头、正文读取、JSON、树处理、PNG 校验的细分计时，兼容不含新字段的旧 APK。2026-10-16 15:22 起新 APK 的首次及 3 次后续观察均为 294 节点；后续完整采集中位 6683 ms，其中 PNG 编码中位 2848 ms、范围 2707–3310 ms，已明确为主要瓶颈。纯树、截图 API、窗口后检及 Base64 的独立中位分别为 861、87、60、55 ms。

主机等待响应头中位 5344.544 ms，已经包含设备端工作，不能再与 PNG 编码等分段相加；正文读取、JSON 解析、树处理和 PNG 校验的独立中位分别为 74.289、6.746、25.612、77.370 ms。该批后续只有 3 次、页面动态变化，不报 P95，也不能与旧批次的 5864 ms 比较后宣称提速或退步。

焦点读取已增加有界的查询方式缓存：按 ADB 路径和设备区分，最多 32 项，闲置 5 分钟过期；每次仍读取最新焦点。本机 `displays` 缺全局焦点屏证据，因此学习完整 `dumpsys window`，不单独缓存 `displays`。明确空焦点、非主屏、歧义、命令失败或取消会停止并使缓存失效。只读交错 10 对测量的旧/新中位为 151.442 / 92.303 ms，命令数从 2 降至 1，单次焦点查询减少 59.139 ms（39%）；这不代表完整采集或任务提速 39%。旧流程约 0.49 秒的无效探测只作为线索，不作为实测节省量。完整依据见[同机对照](AUTOMATION_DEVICE_BENCHMARK.md#耗时定位与下一步)。

清缓存和倒置空矩形裁剪修正已在单页两次完整观察中通过：971 节点个人页的树遍历为 8393 / 8328 ms，PNG 编码 1906 / 1982 ms，完整采集 13587 / 12873 ms。本页主要耗时是新鲜树遍历，不能与此前 294 节点视频页作速度对照，也不能恢复旧缓存换速度。

随后实施两项优化：API 33+ 子节点采用深度优先不可中断预取，每批最多 50 节点，仍完整遍历且每次清缓存；不透明 sRGB/ARGB_8888 图片采用逐行无损 PNG 编码，其余格式原生回退。相同 Bitmap 的 Android 5 次编码对照中位从 1775.691 ms 降到 327.400 ms，逐像素一致，文件增加 19.9%；alpha/P3/F16 回退输出与原生一致。这只确认编码局部收益。

旧版与新版均完成同页首采加后续 5 次，全部 971 节点并通过主机校验；后续采集中位 **11584 → 6236 ms**，树遍历 **8098 → 3885 ms**，PNG **1746 → 421 ms**。两轮拓扑、字段集合、非几何语义和个人页 110 个可见后代的几何签名一致；底栏原有的 15 个可见节点坐标变化单列，不能宣称整树完全相同。PNG 字节数中位增加 19.9%。相关 118 项测试及类型检查、桌面和 Helper 构建在实现轮通过，本次只补真机采样和文档；产品会话已停止。详见[新鲜树与 PNG 对照记录](AUTOMATION_DEVICE_BENCHMARK.md#helper-fresh-tree-png)。

### 10.3 性能验收目标

以下是工程验收目标；P0/P1 已有源码与离线覆盖，真机性能目标尚未实测兑现：

| 阶段 | 目标 |
| --- | --- |
| P0 | 所有成功、失败、取消动作都可定位主要耗时阶段 |
| P1 | 明确目标的单步正常路径只需一次工具调用；不再为了刷新身份额外要求外部采集 |
| P1 | 标准多步场景的工具调用数相对受控基线减少至少 50%；需要视觉确认的次数单列 |
| P1–P2 | 完整任务中位经过时间相对受控基线减少至少 30%，同时说明模型时间波动 |
| P3 | 热态完整观察中位耗时比同机 UIAutomator 基线减少至少 50%；未达到则不默认切换 |
| 全阶段 | 无重复输入、无错误目标；无充分证据时不能宣布成功或到达底部 |

这些目标以 P0 建立的受控基线为参照，不直接拿本次含上下文恢复的 9 分 8 秒计算提升比例。若未达标，应按分段数据调整方案，不能隐藏失败样本。
