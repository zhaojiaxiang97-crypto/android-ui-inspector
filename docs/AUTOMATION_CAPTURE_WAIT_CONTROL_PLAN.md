日期：2026-10-25。状态：**参考工装、隔离入口及恢复流程已通过离线验证；未启动真机入口，实际间隔匹配及开销未验证**。

方案的固定条件和矩阵保持，后续内部工装只做了合成观察离线验证，见[实现结果](/Users/zhaojiaxiang/.codex/worktrees/navigation-observation-audit/开源项目2/.benchmarks/capture-reference-pair-offline-20261025/RESULTS.md)。旧 P1 的 −6.584% 稳定性失败不改写；此前离线分析的12次预热、12次测量不加入新实验。原产品校验和5%门槛均保持。

## 1. 要回答的问题及边界

已有小页两轮 capture 243→242ms、wait 首帧219→227ms、次帧246→223ms。树阶段均值差−5.333ms主要落在getChild墙钟−5.321ms，但不能确定是调用类型、先后顺序、前序采集状态还是系统等待。详见[已有样本分析](/Users/zhaojiaxiang/.codex/worktrees/navigation-observation-audit/开源项目2/.benchmarks/helper-cadence-offline-20261025/RESULTS.md)。

需要区分三件事：相同采样位置下等待链路与普通capture是否不同；第二次完整观察是否因连续采集而改变；getChild波动发生在运行、排队、远端处理还是回调接收后。

wait次帧必须晚于首帧，且保持350ms等待。不能随机打乱首/次帧，不能称为三角色完全随机实验。以下设计通过位置相同的参考帧和顺序交叉减少混杂；仍无法观察的角色×前序状态交互必须保留为限制。

## 2. 固定条件与进入门槛

仅限DEVICE_SERIAL、自有Debug App com.androiduiinspector.sdkfree，1080×2400、旋转0。小/大页仍69/758节点，Helper及测试App的Debug标记、签名、预取、清缓存、节点字段及编译设置固定。无业务输入，不主动GC、不强制编译、不锁频来制造稳定。

沿用修正版调度：每阶段先完成离线检查和必要构建，再重建Helper；确认新PID后立即启动驱动等待配对/授权。首次预热capture固定在确认后180000ms，允许迟到0–500ms；准备超时即落盘失败，不顺延。预热固定小/大/小/大四条capture+严格双帧wait，共12帧，不追加。

先用两个全新原版进程Q1/Q2执行原测量节奏：每页两条capture+wait，每页六帧。组内前/后三帧完整观察和设备树中位数的绝对漂移均≤5%；Q2与Q1各页六帧中位数的完整观察和设备树漂移也均≤5%。任一失败立即停止此新实验，不挑选另两个通过的进程，也不启用后续参考/追踪候选。旧P1不会被这两个新编号替代。

保留完整树、唯一性、来源/设备/窗口/屏幕身份、新鲜度、遮挡、两份不同新帧、原期限及重试预算、1000ms输入门卫、unknown停机、32MiB及原报告读取预算。参考帧和追踪提示都不能授权输入或代替严格wait证据。

## 3. 四种三帧区组

C0为正常独立capture。W1/W2为一次真实严格组合wait的首/次帧，仍验证visible与enabled。R1/R2为“两次完整capture”的参考对，不冒充wait。

| 处理 | 三帧原顺序 | 对照用途 |
| --- | --- | --- |
| A | C0 → W1 → W2 | 原有节奏 |
| B | W1 → W2 → C0 | 交换独立capture与完整wait对的顺序 |
| C | C0 → R1 → R2 | 与A相同位置的普通capture参考 |
| D | R1 → R2 → C0 | 与B相同位置的普通capture参考 |

W1/W2和R1/R2都必须相邻；不得在两帧之间插入其他采集、切页、能力查询、导出或分析。

内部入口DebugSession.captureReferencePair已复用既有完整capture执行链、快照接纳、逐步持久化和原校验，在同一进程顺序执行两次完整采集。当前350ms等待从R1完整持久化后开始，额外处理开销如实保留，不能据此声称观察边界已等时。两份独立快照、产品步骤和最终计时均保存；不新增公开产品命令、不调用任意坐标或私有平台hook。参考对只表示capture参考完成，不计入wait成功数；额外用原双帧条件校验两帧目标可见/启用。

普通两个CLI capture之间有命令启动及报告落盘开销，不能直接冒充等时参考。工装先做离线调用链检查和延迟/完整性测试，未来再核对实际观察间隔：同页、同摆放的参考对与wait对，观察结束到下一观察开始的间隔中位差绝对值须≤5ms。该5ms是新增工装匹配条件，不替代任何5%门槛；只判断匹配，不补偿计时、不缩短350ms、不删除不匹配帧。

间隔匹配在完整固定矩阵结束后按页面、摆放分别计算，失败则整组拒绝纯角色归因，不能删除不匹配帧或重跑。若保留原持久化后做不到等时间隔，后续只能报告A/B顺序与包含执行器开销的链路差异，不为凑时序绕过持久化或改产品执行器。R1/R2的可实现性和开销目前未经真机验证。

## 4. 平衡顺序、采样数与停止规则

四个独立进程使用下表固定顺序，每个字母均是上表完整三帧区组；每页各执行一遍。每个区组内不切页，同一页面四区组连续运行，中间不重启App。仅在两页之间按固定流程启动对应测试Activity并确认就绪，不靠额外capture准备页面。

| 独立进程 | 页面顺序 | 每页区组顺序 |
| --- | --- | --- |
| I1 | 小→大 | A、B、D、C |
| I2 | 大→小 | B、C、A、D |
| I3 | 小→大 | C、D、B、A |
| I4 | 大→小 | D、A、C、B |

每种处理在第一至第四区组位置各出现一次；不同处理的12种有向相邻关系各一次。每页诊断区组共48帧，两页96帧。平衡的是区组时期和相邻处理，**不是强行把W2放到第一帧**。

各I进程沿用固定180秒和12帧预热。每页诊断前、后分别安排原capture+wait两条流程的六帧基线段，每段保持原前/后三帧5%检查；前/后六帧中位数的完整观察与树阶段漂移也均≤5%。资格、基线、诊断数据分开统计，不把异构参考组塞进原六帧门槛，也不用参考结果替代原校验。

Q1/Q2合计48帧（预热24、测量24）；I1–I4合计240帧（预热48、前后基线96、诊断96）。资格加无追踪矩阵全部通过时固定上限288帧，工装/追踪先导与校准按第7节另列，均不是本轮已执行数。未来若任一前置或基线门槛失败则提前终止、保存未完成矩阵；不得为了平衡强行补齐或追加“较稳”的一轮。

诊断会话预先按完整三帧区组或完整六帧基线段分片，不拆wait对；只在固定边界换会话，所有处理采用相同规则。资格组沿用原12帧预热+12帧测量的报告布局。实施前以既有最大附件和最终计时预留核算每片；超过原32MiB即拒绝，不提高上限、不丢旧帧。授权/归档/切页成本单独记账。

## 5. 分析方式：先看原值，再作条件对照

每帧保留进程/服务/会话、页面、处理、时期、帧位、前一角色、前序页面、观察序号、所有新快照ID，以及完整观察、树、getChild、本地处理和独立getRoot计时。记录距Helper重建、距页面就绪、前帧结束的实际间隔。不得在计时中新增轮询来“测量”这些间隔。

先分别报告每页、进程、时期的原值与原5%基线结果，再比较A/C和B/D的同位置W1−R1、W2−R2。另算每对的“次帧−首帧”，比较(W2−W1)−(R2−R1)，仅作在相同间隔/摆放条件下的差分估计。A/B以及C/D的差值用来检查把整个对移到前面之后是否改变结果。

不把同一对的两帧当独立重复，不混合大小页，不合并资格和诊断，不筛慢帧。四个进程才是独立进程重复；若按进程/时期分层后方向不一致，结论为不确定。只有共同位置和匹配间隔上的比较可解释，不能用回归模型填补不存在的角色组合，不能宣称消除了全部非线性交互。

均值用于互斥子阶段差值闭合，中位数用于原门槛；不相加不同子阶段中位数，也不把主机和设备时钟相减。主机观察偏移、设备elapsedRealtime、Trace时钟分别保存；跨域仅用明确请求/观察关联及Trace时钟映射。

## 6. 需要补充的追踪

优先复用已有隔离计时和Trace能力，不重复证明已知事实；当前P1没有这些事件，不能把历史trace补贴到P1。以下能力都需在将来的实际包和设备上重新确认。

| 追踪 | 对象与必要字段 | 能回答什么 / 不能回答什么 |
| --- | --- | --- |
| 观察与调用边界 | 匿名观察编号、角色、captureId映射；getChild起止、调用线程tid、调用序号及该线程CPU差值；初始与后验getRoot另列 | 将慢帧拆到具体调用；墙钟−本线程CPU只是残差，不等于Binder传输 |
| 调度与唤醒 | Helper扫描/回调线程、目标App主线程、可识别的系统服务线程；sched_switch、sched_waking及线程生命周期 | 区分Running、Runnable未获CPU、Sleeping/阻塞；睡眠状态本身不说明等待对象 |
| Binder及目标端 | 可用的transaction/received事件、事务标识、发送/接收tid、目标Accessibility处理/Provider区间、回调收发 | 唯一关联请求、目标处理与回调；异步请求不能用同步RPC耗时代替全链路 |
| 频率及空闲 | 各CPU的可用频率/idle事件、事件覆盖及初始状态 | 观察频率/核迁移与慢调用的重叠；旧sysfs频率null不能当0，也不能据相关性直接断定降频因果 |
| ART运行时 | Helper与目标App中实际可用的GC暂停/线程挂起、并发GC、JIT编译事件及线程 | 区分慢区间是否与运行时工作重叠；缺事件不等于没有GC/JIT，不改GC类型、CheckJNI或编译策略 |
| 方法级CPU，按需增加 | Helper扫描与Binder回调接收线程；先沿用100Hz CPU时钟、32KiB DWARF栈，核对完整符号和丢样 | 区分Parcel解包、节点还原、缓存写入与通知路径的CPU权重；不能把100Hz样本换成精确的10余ms墙钟差 |

调度/频率方案依据[Perfetto调度文档](https://perfetto.dev/docs/data-sources/cpu-scheduling)与[频率文档](https://perfetto.dev/docs/data-sources/cpu-freq)。固定边界用[ATrace](https://perfetto.dev/docs/data-sources/atrace)；CPU能力依据[AOSP Simpleperf](https://android.googlesource.com/platform/system/extras/+/master/simpleperf/doc/README.md)。GC和JIT解释分别参考[AOSP GC](https://source.android.com/docs/core/runtime/gc-debug)、[AOSP JIT](https://source.android.com/docs/core/runtime/jit-compiler)。这些是工具能力依据，不代表本机每个事件当前都可用。

固定标记仅写数字序号和阶段，不写控件文本；不为获取回调内部方法而反射hook平台类或扩大权限。回调缺唯一事务关联就保留未关联记录，不按时间最近强配。缓存写入常在扫描线程，不能把整个缓存类CPU都归给接收线程。

先将每个getChild墙钟按该调用线程的互斥Running/Runnable/Sleeping/未知区间闭合；另展示目标端和回调线程重叠工作。两条线程并行区间、嵌套Parcel/还原方法不能重复相加。CPU方法比例和调度墙钟分别记账。

## 7. 追踪开销与关联诊断的进入条件

执行顺序固定为：离线工装自检→Q1/Q2资格→如有工装/包改动先校准其关闭态→无追踪平衡矩阵及间隔匹配→按需T1/T2开销校准→短时关联。任何进入条件未过即不启动后项。无追踪的角色/顺序对照负责比较处理差异；带追踪的小批只定位机制，不与无追踪耗时混成生产收益。

先检查实际数据源、符号、请求边界和时钟覆盖。每级可用性先导固定大小页各一条C0+W流程，共6帧，预热另计12帧；先导只验证可用性，不给性能结论。缺关键事件则该假设保持未知。

如需新增诊断APK/桌面工装，先做原版→探针关闭版→原版的同源码校准：每阶段独立进程、原180秒/12帧预热、每页原六帧测量；两个原版前后漂移和关闭版开销均须满足原5%。关闭探针不自动视为零成本。Debug条件不变，不引入新的Debug/非Debug对照。

追踪级别按需逐层开启：
- T1：必要边界和每调用墙钟/线程CPU，加调度、Binder、可用的频率/idle和ART事件。
- T2：T1加方法级CPU采样；仅当T1仍不能定位本地回调处理且符号可用时进入。

每级均需独立off/on/on/off校准，大小页各四条原C0+W流程，共24帧测量，预热另计12帧。每页off两条、on两条分别形成原六帧门槛，完整观察及树阶段均检查5%；off前后不稳定、首次完整采集失败、录制警告或Trace关键数据丢失都拒绝。on相对off的完整观察及树中位增幅均不得超过5%；负差只记波动。T2必须重新验证组合开销，不能把T1和CPU单独历史通过当作组合通过。

通过后短时关联诊断固定A/B/D/C顺序，大小页各四区组，共24帧；固定12帧预热及前后基线24帧另记。本阶段只做机制关联，不用这一行不完整的平衡矩阵再估计类型因果。每个三帧区组一个预定10秒追踪窗口，启停在采集区间外；窗口没覆盖完整区组则记追踪失败，不事后拉长或追着最慢帧补录。

每级校准/先导/关联均独立新编号和会话，不借用旧P1样本。所有计划调用都计入尝试数；无警告、全部完整、可关联、无丢失且开销过门槛，才允许机制结论。若100Hz方法样本不足就报告不足，不临时加频率、延时或补样。
