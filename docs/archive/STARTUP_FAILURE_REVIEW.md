### 先补什么

当前`InspectorTree`到任务结束才打印posted/entered，旧12秒窗口观察器在窗口出现后就退出，两者都不能触发本次SDK排队观察。不要直接复用旧触发规则。

APK摘要/SDK来源/进程startTicks需在观察前验证；APK不能在排队期间重新读取。事件中的`tree-queue-v1`仅是协议标识，不是SDK构建摘要。sdk-source-v1来源指纹、单次库和生产请求/转发适配已接，独立样例已部署，业务尚未部署该修正，真实排队观察未完成。缺失时拒绝，不能填默认值当已确认。

### 一次观察顺序

1. 用户授权一次启动/采集；绑定已验证包、SDK构建、PID/startTicks、processInstance、requestId。订阅仅该请求的诊断通知，无自动重试。
2. `scripts/diagnostics/sdk/sdk-queue-stack-policy.ts`现已实现本地门禁：通知身份完全匹配、请求仍有效、任务未进入/结束，设备已排队500–2499ms，通知在主机收到后不超过250ms才允许预留一次观察。失败或未命中不再附加第二次。
3. 独立诊断连接就绪后、暂停前再次检查请求/进程/任务状态。SDK的Binder/LocalSocket共用 `read-tree-task` 授权：arg为请求编号、extras绑定processInstance，仅shell UID2000和Debug App可读。查询在本Provider的capture监视器之外读取标量，不进UI队列；不走正在等待capture的串行socket。返回JSON含协议、请求/实例/PID、kind、posted/entered/ended/settled/observed。错误身份/未开启/非最近任务拒绝；已结束任务只返回结束状态，不能授权暂停。两客户端上限与普通数据串行不变，真实Android并发性未验证。
4. 复用现有`withSuspendedMain`及`withOwnedForward`，只暂停main、最多读32帧，不调用业务方法或全VM暂停。读取帧后先恢复并确认SuspendCount=0，之后再解析类名；只删除自己的转发。连接/命令超时有界，取消也必须先恢复再退出，不中途丢掉恢复步骤。
5. 收尾核对当次entered/settled及进程身份。仅当取栈前后的**保守设备时间范围**完全落在posted到entered（未进入则settled）之间，且恢复和清理均成功，才记“命中排队区间”。使用暂停前/恢复后设备单调时钟读数夹住实际采样，并保留读数精度与不确定范围；主机和设备时间不能直接相减。边界重叠或缺字段记未覆盖。

本地policy只预留和核查传入证据，不创建连接、执行取栈或证明这些时间/身份来自设备。暂停会扰动业务及3秒任务超时，必须保留pauseMs；不能将本轮当无扰动性能或冷启动成功验收。即使命中某方法，单点栈仍不能证明该方法持续阻塞或自身是根因。

### 启动前置依赖与取证分工

本轮源码复核的结论不是“SDK一定有错”，而是最早启动观察不能要求SDK已经可用。SDK的`HierarchyProvider.call`在采集锁外读取标量、`onCreate`只登记生命周期；但到达这些方法前仍依赖Android发布Provider。

Android 14 AOSP在`handleBindApplication`内先创建Application，再安装Provider并统一发布，然后调用Application.onCreate；因此PID、Provider发布和App窗口分别是不同状态。[ActivityThread（android-14.0.0_r14）](https://android.googlesource.com/platform/frameworks/base/+/refs/tags/android-14.0.0_r14/core/java/android/app/ActivityThread.java)

shell的content先向系统取得Provider；外部调用可能在发布前等待，必要时系统还可能拉起Provider进程。只读SDK方法不等于这个命令不经过启动依赖，也不等于主机控制系统进程生命周期。[ContentProviderHelper（同标签）](https://android.googlesource.com/platform/frameworks/base/+/refs/tags/android-14.0.0_r14/services/core/java/com/android/server/am/ContentProviderHelper.java)

content在Provider访问异常时写stderr并捕获异常，没有在该分支主动非零退出；无效Bundle同样不代表身份成功。主机原先丢弃成功退出的stderr，已修正保留输出、严格解析与错误留证；正常daemon提示不误判，明确访问错误即使伴随有效回复也拒绝。[Content命令（同标签）](https://android.googlesource.com/platform/frameworks/base/+/refs/tags/android-14.0.0_r14/cmds/content/src/com/android/commands/content/Content.java)

以上只是AOSP基线及本仓库代码关系；厂商实现和上次失败的具体路径没有证据，不能从缺失的退出信息推断超时或未发布。本轮真实本机子进程只模拟退出0+stderr，未复现Android Binder等待；旧失败原样保留。

### 安全模式触发与完成路径：只读源码及保存APK复核

本地复核已完成，19项离线产物检查通过。保存的已验APK前后SHA与上轮安装核验相同；实际反编译指令确认启动计数、候选门控、5个通知计数、4秒等待参数和退出门控与本地所读源码一致。不是仅凭同名类推测；仍非整个源码/包完全一致、动态补丁执行或手机当前安装状态证明。源码/字节码/路径和字段名只保存在忽略目录`.benchmarks/startup-safe-mode-review-dq1czj/`，不复制到公开仓库。

已确认机制：

- 主进程进入启动阶段即增加持久计数；阈值须为正且计数超过阈值才进入候选。默认阈值2，即默认第三次未完成退出清零的启动触发候选；实际设备阈值/计数未知。
- 候选仍需检查异常和退出记录。缺少有效异常、排除用户主动结束/安装等退出后不足阈值时可提前返回；所以不能仅凭反复强停就断言一定进入完整等待。
- 完整路径先启动5组修复/上报工作并同步准备本地补丁，然后等待累计5个通知；等待参数为2+2秒，超时标记后继续，捕获中断后也不在此无限等待。4秒仅是该次等待参数，不是整个安全模式/冷启动总耗时上限，也不证明上轮实际等了4秒。
- **页面出现不等于计数清零。** 正常退出路径还取决于启动完成回调及主业务全量配置获取成功两个通知；没有成功通知时可能保留旧计数。当前实现用总计数而非按通知类型去重，不能只凭计数推断两类事件各发生一次。

| 通知来源 | 已读到的结束路径与限制 |
| --- | --- |
| 异常记录上报 | 工作线程正常/异常结束均在收尾发通知；工作线程创建前的准备异常未必发通知。 |
| 清理配置获取 | 工作线程收尾发通知；准备请求或创建线程之前异常没有统一补通知。 |
| 日志文件上报 | 明确跳过也发通知，工作线程收尾发通知；上传前准备异常存在不发通知分支。 |
| 修复配置获取 | 失败可回调空结果；回调处理后才发通知，不是统一收尾，处理异常可能漏通知。 |
| 补丁事件 | 指定事件发通知，未见按任务去重；多次事件可能多次扣减。 |

通知仅表示计数扣减，不保证业务成功；修复配置失败也可能正常完成通知但“结束”标志仍为false。阶段标志、总通知数和任务成功是三种不同证据，不能据一个false猜出唯一未完成任务。少通知会让这次等待走到超时，重复通知可能让等待更早结束；这里只是已证代码风险，不是上轮设备故障原因。
