# D19：读取登记容量与拒绝原因

更新：2026-10-18。状态：容量修复和拒绝诊断已实现，通过本地及真机只读验证；连续导航门槛未通过，候选入口默认关闭。原 Helper 已恢复。

## 问题和改动

[D18](AUTOMATION_EXECUTOR_BUDGET_D18.md)中，同一会话第三轮返回后遇到读取拒绝。原登记表把运行中、已完成及取消先到的记录合计限制为 32 条；动画恢复产生额外读取，正常连续计划也会耗尽名额。

这轮沿用原控制器和同一张登记表，分别限制准入：

| 限制 | 数量 | 用途 |
| --- | --- | --- |
| 运行中读取 | 32 | 限制工作线程持有的请求；取消后尚未退出的线程仍计入 |
| 取消先到、读取尚未开始 | 32 | 防止预取消记录无限增长；不占运行名额 |
| 所有身份记录 | 256 | 给已结束请求保留防重放空间；同时限制总内存中的登记数量 |

已结束请求不再占运行名额，但继续占总记录额度。过期规则保持为“原请求截止时间后 60 秒，且工作线程已经退出”。不使用 LRU 提前淘汰、不强行释放采集锁，也不因表满删除未到期记录。

查找既有身份先于新请求准入。满表时，既有请求仍可取消；重复读取仍被拒绝，旧取消不能影响新快照。新请求超过任一相应上限时继续返回 `capacity`，桌面不补发输入或自动重试。

桌面为严格匹配的失败响应保留有限原因，例如 `helper-control-capacity`、`helper-control-timeout`。未知原因、额外字段和身份不匹配仍返回通用错误，不把服务端任意字符串写进报告。该原因只用于拒绝诊断，不作为观察完整或身份可信的证明。错误沿用原步骤和报告格式，不增加新执行接口。

## 本地验证

173 项相关测试、类型检查和完整构建通过；候选 Helper Android 构建通过。

- 生产 Java 控制器夹具连续完成 100 次读取，旧请求仍不能重放，迟到取消不改写新证据。
- 256 条总记录硬上限、32 条运行名额及 32 条预取消名额均验证；即使时间已经过期，运行中记录也不会被淘汰。线程退出后才释放运行名额。
- 保留树遍历、PNG、JSON、发布四阶段取消，以及原子完成、授权变化、排队预算和旧证据竞争验证。
- HTTP 夹具覆盖全部允许的错误原因、未知原因和额外字段；拒绝后仅取消原请求，不回退到其他采集来源。
- 容量错误发生在输入后时，报告保留具体原因；只发送原来的一次输入，没有恢复读取或第二次输入。

第二批失败时，同一服务及会话已累计发起 38 次协议读取，没有再次出现原来的 32 条容量拒绝。它可以支持容量修复的局部结论，不能把两批的通过轮次拼成三轮连续通过。

### 最终候选的固定页面与容量验证

随后补充一个本地边界：排队超时、尚未开始的失败记录不能误占“取消先到”的名额。最终候选为 `source-IJPRcd`；没有在它上面宣称已完成三轮导航。

| 场景 | 结果 |
| --- | --- |
| 同一会话固定页面连续读取 40 次 | 40/40 成功，40 个不同新快照，墙钟 56.128 秒；没有输入、重启或分拆会话 |
| 32 条取消先到记录及第 33 条 | 前 32 条接受，第 33 条返回 `capacity` |
| 预取消额度满后正常读取 | 第 41 次完整读取成功，证明预取消记录不占运行名额 |
| 主动构造 1 ms 预算读取，填满总登记表 | 第 187 次尝试返回 `capacity`，此前短预算结果均保留；这是有意的容量测试，不是正常采集成功率 |
| 总登记满后取消既有记录 | 仍返回该请求原来的 `cancelled` 状态 |
| 总登记满后通过桌面采集 | 安全拒绝，报告为 `helper-control-capacity`，没有接受新快照，也没有输入或自动回退 |

40 次成功读取在旧记录尚未到期时已跨过原 32 条上限，排除了靠等待旧记录自然清理通过的情况。最终候选的压力测试另用一个会话，是因为安装了补充边界后的新 APK；单次 40 连读过程中没有重置会话或服务。
