# AI 预生成计划与自动执行器：方案建议

日期：2026-10-16。状态：桌面端第一阶段已实现，使用方法与本版边界见[执行器说明](../../AUTOMATION_PLAN_EXECUTOR.md)。手机端解释器仍为后续方案；本次没有操作手机。

## 结论

可以实现。AI 先把任务写成结构化操作计划，执行器自行完成定位、等待、操作和验证，遇到计划外情况再交回 AI。正常路径不需要每一步都经过模型。

执行器可以放在桌面，也可以放在手机。**先复用当前桌面执行链完成整段计划执行，再将经过测速确认的慢环节下沉到手机端**，是当前项目成本最低、最容易验证的路线。直接把解释器放到手机上，并不会自动解决窗口识别、列表终点或系统拒绝输入的问题。

## 它与目前的区别

目前人工式调试经常是：AI 读取页面 → 思考 → 调一个动作 → 查看结果 → 再思考。新的正常路径是：AI 生成计划 → 一次提交 → 执行器连续执行并记录结果 → 完成后统一汇报。每一步仍然读取必要状态、核对目标和验证结果，只是无需每次询问 AI。

| 职责 | 谁负责 |
| --- | --- |
| 理解“进入我的收藏，播放最后一条”等自然语言 | AI |
| 把任务转换为动作、条件和有限分支 | AI 生成，执行前校验 |
| 实时查找控件、等待条件、点击、滚动、返回 | 执行器 |
| 检查是否进入预期页面，记录每步耗时与证据 | 执行器 |
| 遇到未知弹窗、多个同名目标、页面结构变化 | 停止当前输入，将现场交给 AI |
| 修改后续计划 | AI 重新生成待执行部分，保留原执行记录 |

不能提前固定所有坐标或缓存一套控件编号。每一步都要在当时的页面重新解析目标；“最后一条视频”必须先确认列表终点，再从当时的列表确定最后条目。

## 当前项目已经具备的基础

- [多轮回测脚本](../../../scripts/automation-ui-regression.ts)已经能从结构化计划连续调用单步操作和连续滚动，并保存请求编号、逐步证据、耗时和停止原因。正常执行不依赖 AI 逐步发指令。它目前是固定回测工具，还不是带分支和异常交接的通用产品执行器。
- [任务定义](../../../shared/debug-task.ts)和[任务检查器](../../../electron/automation/debug-task-execution.ts)支持目标、阶段条件和最终验收。这里的任务定义主要描述“如何验收”，并不自动推导或执行到达目标的动作。
- [步骤执行链](../../../electron/automation/debug-step-executor.ts)已经处理动作前后观察、定位与验证，可继续复用。
- [Inspector 手机端观察协议](../../../scripts/helper-templates/InspectorObservation.java)和[观察客户端](../../../electron/capture/helper-observation.ts)目前接入的是读取能力。[准备脚本](../../../scripts/prepare-recognition-helper.ts)固定的 Artemis Helper APK 本身也保留点击、滑动等原子动作接口，但 Inspector 尚未将其接入当前动作执行链，它也不是整段计划解释器。要把动作、等待和计划状态一起放进手机，仍需补齐受控执行协议及授权、请求记录和结果验证。

因此，缺的主要是产品内的整段计划运行入口，以及动态目标、有限分支和异常交接，不需要重新造一套所有底层能力。

## 桌面执行与手机执行怎么选

| 方案 | 收益 | 成本与限制 |
| --- | --- | --- |
| 桌面常驻计划执行器 | 省掉逐步 AI 往返；直接复用现有授权、动作和证据链 | 控件树、截图和设备通信的耗时仍存在 |
| 手机端执行器 | 可在手机内定位、等待和操作，减少全量树传输和部分命令往返 | 要增加设备任务状态、取消、重连和授权同步；输入能力仍受 Android 限制 |
| 两端协作 | 桌面管理计划和证据，手机执行有边界的局部片段 | 需要明确同一任务由谁派发，防止两端重复执行 |

建议先做第一种。这里的“本地”指桌面进程内自动执行，不是每步再启动一次外部命令。手机端下沉可从“定位目标 → 等待可操作 → 执行一次 → 等待预期”的有限片段开始，不必一开始支持任意脚本。

Android 的无障碍服务提供手势派发及回调，但需要相应服务能力，回调也不能代替业务结果验证；UI Automator 同样提供元素定位、等待和设备交互。两者是可选设备适配方式，不能因当前命令失败就在同一步自动换路线重发。[Android 手势接口](https://developer.android.com/reference/android/accessibilityservice/AccessibilityService#dispatchGesture(android.accessibilityservice.GestureDescription,%20android.accessibilityservice.AccessibilityService.GestureResultCallback,%20android.os.Handler))、[UI Automator 官方说明](https://developer.android.com/training/testing/other-components/ui-automator)。

手机端执行器可以是独立测试组件，不要求向被测 App 引入 SDK；SDK 可继续作为获取更深属性的可选能力。

## 脚本应当长什么样

优先选择可校验的 JSON 操作计划；需要更易手写时再考虑 YAML。它表达动作、目标和条件，不开放任意代码执行。下面是语义示意，**不是当前已经支持的可运行脚本或接口**：

```text
目标：打开我的收藏列表最后一条视频
范围：指定设备、指定 Debug App、当前有效授权

1. 如果在播放页，返回，并验证已离开播放页
2. 如果尚未进入个人页，定位底栏“我”，点击并验证个人页
3. 定位“收藏”标签，点击并验证收藏作品列表
4. 在收藏作品列表内向下滚动，直到明确终点；设置最大次数和总时限
5. 在已确认到底的列表中解析最后一个视频条目
6. 重新核对条目的身份、可见区域和可点击状态，点击一次
7. 验证播放器页面；如要求“确实播放”，还需播放状态或进度证据

找不到唯一控件、没有终点证据、授权失效或输入结果未知：
停止，保存现场并交回 AI，不继续后面的步骤
```

“已进入播放器页”和“视频已开始播放”必须分别验收。当前用返回按钮等控件验证页面，不能直接宣称测得播放开始时间。

第一版只需已有点击、返回、滚动、找终点、条件等待，再加有限条件分支和明确的任务结束状态。开始、查询进度、取消可作为产品入口；不需要先引入通用语言解释器。

## 真正能省掉哪些时间

第一步最直接减少的是模型思考、工具往返，以及调用间人工检查和准备参数的空档。手机内执行还可能减少树传输、截图编码与外部命令启动，但收益必须单独测速。

现有新实例准备中，两次点击的产品耗时约8.984秒、7.192秒；四次滚动合计14.630秒。这些已经是产品内部计时，不包含 AI 在两次调用之间思考的时间。**只加脚本执行器不会让这些设备观察和验证自动变成毫秒级**。样本来源见[回测记录](../../AUTOMATION_UI_REGRESSION.md#new-instance-preparation)。

后续可在设备端先做目标范围内的查找与条件等待，事件用于唤醒检查；关键阶段和失败仍保存完整必要证据。不要每一步都做完整3D采集，也不要为了提速取消动作结果验证。观察减量属于后续性能改造，需要证明不会漏掉窗口、遮挡和错误页面。

## 开源项目可借鉴什么

- **Maestro 更接近这个脚本思路。** 它使用声明式 Flow，提供动作、断言、条件和子流程。可借鉴“脚本表达意图，执行器负责等待和验证”的设计；不需要照搬它的所有能力，也不能据此推断其解释器全部在手机里运行。[Flow 文档](https://docs.maestro.dev/maestro-flows)、[条件分支](https://docs.maestro.dev/maestro-flows/flow-control-and-logic/conditions)、[等待机制](https://docs.maestro.dev/maestro-flows/flow-control-and-logic/wait-commands)。
- **Artemis 可借鉴异常交回与计划监督。** 官方说明描述观察与动作循环、动作检查和任务规划；源码配置还允许有限动作串联。因此它也在减少逐动作决策成本，但不能简单等同于“把完整脚本放进手机解释”。本项目更适合把确定流程交给执行器，把计划外判断留给 AI。[Artemis 官方仓库](https://github.com/google/artemis)、[执行配置源码](https://github.com/google/artemis/blob/main/artemis/config/agent.py)。

## 建议落地顺序

1. **桌面整段执行。** 从现有回测执行顺序、请求记录和证据逻辑中复用能力；增加产品计划入口。AI 一次提交，桌面连续执行，异常才返回。先不改变设备输入路线。
2. **用同一真实流程对照。** 比较逐步 AI 调用与计划执行的端到端耗时、产品内部耗时、输入次数、误操作和证据完整性；遇到未知输入不自动重放。当前未完成的真机单轮和10轮仍需单独验收。
3. **按耗时下沉局部片段。** 若设备观察和通信仍是主要瓶颈，再增加手机端受控执行。沿用同一份动作和条件语义，避免两套含义不同的脚本。

每一步输入前仍须核对授权与目标。输入发送前保存唯一编号，断线后先查原结果；无法确定是否执行过时停止，不能保证靠重试获得“恰好一次”。桌面拥有任务状态和取消权；手机端新增执行后还需要短期执行许可，连接失效或许可到期后禁止继续输入。

方案首版仅完成源码核对；当前桌面执行器已按第一阶段落地，见[实现说明与验证记录](../../AUTOMATION_PLAN_EXECUTOR.md)。手机端解释器、同机提速对照及既有系统输入拒绝和列表终点问题仍需分别验收，不从离线测试推断真机提速。
