# D14：完整采集前的窗口就绪探针

更新：2026-10-18。范围：实现单次有界就绪探针并在真机完成首次候选对照；20% 整段目标仍未达成，探针保留为可选调度提示，不改变默认恢复路径。

## 结论

1. **单次探针成本显著低于完整采集**：真机稳定页面探针 31–69ms 返回，完整 Helper 采集 278–662ms；Gifmaker 大页面探针 21–44ms，采集 278–662ms。探针只做一次窗口清单枚举，不截图不编码。
2. **探针能在正确时机捕捉过渡失败**：Gifmaker 冷启动切换瞬间，探针 80ms 预算 8/8 返回 timeout（即未就绪），证明它能在真机复现"读失败"形态；同场景直接采集 8 次里 5 次 incomplete。
3. **但探针的收益门槛未通过**：Gifmaker 冷启动 A/B 对照（探针等待就绪后采集 vs 固定 2.5s 直采），两轮 6+6 与 4+4 样本里 A 方案完成率 1/6、0/4，B 方案 2/6、0/4。样本量小、首启抖动大，**不构成稳定提速证据**。探针等待就绪后仍会读到 display_changed 等 incomplete，说明"探针 ready"与"完整采集就绪"之间仍有 100ms–5s 量级的窗口差。
4. **提前结束失败观察的收益上限有限**：真实 incomplete 快照的耗时拆分显示，树阶段（可提前结束的部分）中位数仅 226ms，后续截图+PNG+后验+Base64 的 post_tree 部分中位数 400ms；即"树不完整立即返回"能省下的总时长上限约 0.4–0.5s/次，远低于 20% 整段目标。D13 的 2.39–2.85s 失败观察成本主要落在已完成的树读取本身，而非可裁剪的后续阶段。

## 已合入能力（本次提交检查点）

- `/inspector/ready`：单次有界窗口清单探针，无选择器、无动作、无额外预算。仅返回 ready/pending 或明确错误码，不产生证据。
- 桌面客户端：`readHelperReadyProbe` + `helperSession.probe`，沿用 pairing、forward 归属、会话互斥与 3s 硬截止。
- 执行器恢复路径：Helper 采集失败后的重试等待前调用一次探针；探针失败不阻塞重试，仅作为调度提示。
- `shared/helper-ready-probe.ts` 协议、`shared/debug-timing.ts` 新增 `helper_ready_probe` 阶段。
- Java 端 `readWindowReadiness` 使用 Java 8 兼容 switch 与错误封装；`Capture` 类签名不变，避免影响切片测试。

## 与 D13 的关系

D13 确认了窗口切换期重复读取的三个阶段（Activity 缺失、焦点空档、窗口展开），并验证了"专门错误分类+额外重读"候选未通过门槛。D14 改从**完整采集前的短时探针**入手，避免完整采集后再拒绝。本次实现的是第 1、2 步：探针协议与调度接入；第 3 步（树已明确不完整时提前结束）经真实耗时拆分验证，收益上限不足，按预设停止条件不再扩大该方向。

## 后续边界

- 探针保留为**可选调度提示**，默认恢复路径不变；未接入自动重试循环。
- 若后续观察到"窗口就绪提示"与完整采集之间的稳定窗口差缩小（如 Helper 增加 onAccessibilityEvent 驱动的 active 观察缓冲），可重启该方向。
- 探针在 Gifmaker 冷启动首启后的 500ms 内连续返回 `display_changed`（预期行为），因此不能作为冷启动完整就绪的唯一信号。
- 本次未验证：横移/旋转切换、多窗口、多设备、CLI/MCP 路径。
