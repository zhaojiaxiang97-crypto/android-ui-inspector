## 本次范围

先对比同一手机、同一 App 页面上的 UIAutomator 与 Helper 观察耗时，再验证点击、返回及连续滚动。观察测速不发送手机输入；只有完成用户授权后才执行实时采集。

- 两种方式各记录 1 次首采及至少 10 次后续采集，默认分批运行：先 UIAutomator，再 Helper。首采仅指本次测速的首次请求，不代表手机、App 或 Helper 的冷启动；不为测速强制重启业务 App。
- 同时记录完整 CLI 往返和产品内部采集耗时，首采单列，后续报告中位数、最大值；至少 30 个后续样本才计算 P95。
- 保留失败样本，失败即停止；不自动切换来源、不重新发送输入、不自动延长授权。
- 节点数量、公开几何信息和来源分别记录；节点数不同不直接视为数据错误，需要核对实际目标及可见性。
- 脚本不保存页面文本、截图或令牌。CLI 未公开的服务和窗口身份不能伪装为已测得，实际仍由产品内部校验。
- 观察提速不代表整条自动化任务达到同样比例；动作正确性和端到端耗时另外记录。

## 实机发现与修正

首次安装出现手机系统确认窗口，随后返回 `INSTALL_FAILED_USER_RESTRICTED: Install canceled by user`，安装没有成功。该结果不能区分用户主动取消、系统限制或确认超时。

用户回复准备好后，第二次安装返回 `Success`，随后手动开启服务并完成桌面授权。安装问题已解除。

### 隐藏节点的 Android 原始矩形

第一次对照中，UIAutomator 成功，Helper 因字段校验失败而停止。实际协议诊断发现 294 个节点中有 106 个明确隐藏节点，原始矩形倒置，例如 `[1122,0][1080,2355]`、`[14,0][377,-1798]`，可见边界均为 `[0,0][0,0]`。

桌面现在仅对“明确隐藏且可见边界全零”的节点保留该原始诊断信息；可见节点、非空可见边界、缺失可见性或非法矩形仍拒绝。修正后实际 294 个节点全部通过完整性校验，隐藏节点不能通过可见性断言。48 项相关测试、主工作树类型检查和构建、原目录构建通过。

### 交替采样会干扰 Helper 服务

第二次对照依次得到 UIAutomator 4952 ms、Helper 3695 ms、UIAutomator 6067 ms，随后 Helper 报告服务实例改变，测试立即停止。

当前 UIA 路径调用系统 `uiautomator dump`；[AOSP 包装器](https://android.googlesource.com/platform/prebuilts/fullsdk/sources/android-31/+/refs/heads/main/com/android/uiautomator/core/UiAutomationShellWrapper.java)调用默认 `UiAutomation.connect()`，而 [Android 官方文档](https://developer.android.com/reference/android/app/UiAutomation#FLAG_DONT_SUPPRESS_ACCESSIBILITY_SERVICES)明确说明默认连接会抑制其他无障碍服务。本机系统日志也记录了两次自动化连接/恢复；Helper 的实例 ID 按 AccessibilityService 对象生成。由此推断，交替 UIA 导致服务重新创建，尚未直接记录每次设备端生命周期回调。

保留服务重启保护。结束已绑定旧服务的会话、重新获得用户授权后，改成整批 UIA → 整批 Helper。脚本新增 `--schedule grouped|interleaved`，默认 `grouped`，原始样本与摘要都保存调度方式。分批有先后顺序和动态页面变化偏差，不能宣称无偏严格实验；反向顺序可另开新授权独立验证。

## 新鲜树与无损 PNG 优化（2026-10-16）

### 实现与安全边界

API 33+ 子节点查询改用 `FLAG_PREFETCH_DESCENDANTS_DEPTH_FIRST | FLAG_PREFETCH_UNINTERRUPTIBLE`。Android 会先完成一批最多 50 个节点的预取，再将结果返回；外层仍逐个遍历全部子节点，不把 50 当作整树上限。每次采集前的 `clearCache()`、隐藏节点、字段、5000 节点/75 深度限制及窗口后检保留；API 30–32 保留原路径。依据：[Android 预取 API](https://developer.android.com/reference/android/view/accessibility/AccessibilityNodeInfo#getChild(int,int))、[AOSP 请求与缓存实现](https://android.googlesource.com/platform/frameworks/base/+/master/core/java/android/view/accessibility/AccessibilityInteractionClient.java)、[服务端预取实现](https://android.googlesource.com/platform/frameworks/base/+/master/core/java/android/view/AccessibilityInteractionController.java)。

PNG 增加逐行 Sub 过滤与 Deflater level 1，仅处理 ARGB_8888、已知 sRGB 且实际全部不透明的图片。alpha、宽色域、F16、未知色彩和其他格式使用原 Bitmap 的原生 PNG 编码；遇到透明像素或快路径输出超限时，丢弃整份部分输出后回退。尺寸、总像素及最终字节数有限制，压缩器异常时释放；截图顺序、原尺寸、主机完整解码校验保持原规则。Android 的 PNG quality 参数无效，不能靠调低 quality 加速。[Bitmap API](https://developer.android.com/reference/android/graphics/Bitmap)、[Android PNG 编码参数](https://developer.android.com/ndk/reference/group/bitmap)。

### 同 Bitmap 编码对照：已通过

### 回测发现并修复的两处问题

1. **局部容器被当成窗口。** Helper 在每个节点都写 `window-id`，原逻辑取最近带该字段的祖先，误把只有 267px 高的 `refresh_layout` 当窗口。底栏因此未被识别，原规划从拍摄按钮上开始，并被 1px 动画变化校验拦住。现在取最外层同窗口根，保留根、可滚动祖先和显式裁剪边界。原样本重算后可用区域为 `[0,2088][1080,2218]`，手势 `(540,2192)→(540,2114)`，通道底边 2217，底栏退出通道；未放宽控件变化或外窗保护。
2. **大图片触发 V8 栈溢出。** 原 Base64 四字符分组重复正则在大 PNG 上抛 `Maximum call stack size exceeded`，失败位于 `helper_png_validation`，树解析此前已通过。现在使用无重复分组的完整匹配，并继续核对长度、16MiB 字节上限、PNG 头、尺寸和完整解码。新增测试在真实 Node 中通过生产读取器读取 Base64 大于 6MiB 的有效 PNG，并拒绝 7 种坏编码；旧代码先复现了同一异常。

修复入口：[滚动几何](../../../electron/automation/debug-scroll-geometry.ts)、[PNG 校验](../../../electron/capture/helper-observation.ts)。回归：[窗口与底栏](../../../tests/debug-scroll-geometry.test.ts)、[真实 Node 大图](../../../tests/helper-observation-large-png.test.ts)。最终相关 **96 项 / 10 文件通过**，类型检查与完整桌面构建通过；源码和测试已同步原仓库，保留原暂存区。此前实现轮的 192 项不与本轮相加。
