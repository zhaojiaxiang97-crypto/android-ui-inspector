# 已授权前台检查并行（D5）

更新：2026-10-17。已实现并接入 Helper 自动观察和条件等待。单次“前台＋屏幕检查”真机中位耗时 **219.106 → 160.336 ms，减少 26.8%**。这是局部收益；[D6 完整业务对照](AUTOMATION_BUSINESS_PERFORMANCE_D6.md)实测完整墙钟中位数减少 3.6%，20% 整段目标未达成。

## 改动与边界

原先 `checkedDebugTarget` 依次读取 Activity、执行 `run-as <目标包> id`、检查焦点。Helper 会话已经知道授权包，因此前两项可以同时读取，等两项都结束后再检查焦点。外层原有的屏幕并行读取继续保留。

- 只有 Helper 自动观察和条件等待的前后边界显式启用；未指定目标包和其他调用继续按原顺序读取。输入发送前的独立目标复核没有切换策略。
- 提前探测只接受经过格式检查的已授权包，不根据未验证的前台输出选择其他包。前台不匹配、不可调试或焦点不符时仍失败。
- 使用 `Promise.allSettled` 等待两项结束，按原顺序处理前台与可调试错误。读取失败或取消后不会遗留查询、继续检查焦点或替换策略重读。
- 每次都重新读取 Activity、可调试状态、焦点和显示信息；动作前后复核、窗口绑定、Helper 服务身份、转发归属和完整观察校验保留。

最终只修改两个生产文件，没有新增依赖、手机端接口、响应解析协议或通用命令执行选项。

## 为什么没有合并到一个 shell

先测试了将 Activity 与 `run-as` 放入一条固定 shell 脚本的候选，分别保存退出状态、严格校验分段结果。移除额外 `sh -c` 后仍无收益：同机 ABBA、每版 20 个正式样本，单次边界中位耗时 **220.837 → 293.165 ms，增加 32.8%**，命令数虽从 4 降到 3，实际更慢。

该候选与专用解析、输出限制和测试均保留在本机实验补丁中，没有合入生产。更早的嵌套 shell 冒烟也更慢，未形成正式本机归档，不纳入上述数值。不能仅凭命令数推算性能，也不能把差额完全归因于 shell 启动；此次没有额外测量手机内部各子进程成本。

## 正式真机对照

使用同一台 Android 14 设备、同一静止测试 Activity。A 为原顺序，B 为并行目标读取；ABBA 四块，每块首样 1 次、正式样本 10 次，共 **44 次成功边界读取，40 次正式样本**。每次核对包名、组件、Activity 实例、焦点窗口与显示几何一致。期间不发送输入、Helper HTTP、截图请求或启动 App。

两种策略均调用同一版模块，仅显式开关不同；外层 target 与 display 仍一起等待，不把两者的重叠耗时相加。计时保留每条命令的类别、状态和区间，不保存命令参数或 dumpsys 原文。
