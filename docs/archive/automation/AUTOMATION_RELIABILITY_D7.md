# 长会话归档与双帧稳定性修正（D7）

更新：2026-10-17。两项修正已合入原目录。**151 项相关测试、类型检查和完整构建通过；同一真机会话连续 3/3 轮完整收藏流程通过，15 次确认输入、0 次未知输入，30 份冻结报告全部重新导入通过。**

## 截图为什么仍会丢

[D6](AUTOMATION_BUSINESS_PERFORMANCE_D6.md) 的问题出在检查点归档时机：脚本先执行一次 `capture`，再执行 `wait`，最后一起导出两个步骤。等待期间，当前步骤已变为 `wait`，前一步 `capture` 引用的历史前置截图可能被正常容量裁剪；迟到的导出无法再取得它。

修正为：**采集完成立即归档，再等待；每个条件等待完成也立即归档。** 多条件检查同样逐个冻结，不等所有条件结束再保存。每份必要归档必须完整，才能继续读取或输入；归档异常、真实缺图及取消仍会停止。已归档的步骤不重复导出，产品步骤计时仍按唯一编号去重。

没有修改报告容量、淘汰策略或导入校验。实时报告仍是有界历史；需要长期保存的完整证据以逐步冻结报告为准。单个当前动作本身装不进预算时仍会失败，此次不承诺实时报告永远保留全部旧附件。

## 双帧为什么会误停

离线重新读取 D6 的 B2-04 原始归档，并通过严格条件检查器重放实际两帧，确认拒绝原因是：`partial 两次精确匹配的控件身份发生变化。` 两帧各只有一个精确匹配，但路径从 `0/0/...` 变为 `0/1/...`。这证明了检查失败的直接原因，尚不能确定业务树为何变化；旧失败不改写。

修正只发生在等待执行中：遇到上述明确的身份变化，允许**一次重新开始双帧确认**，丢弃刚才不一致的两帧，在原步骤期限内再采集两个新帧。新双帧仍必须通过原检查器，包含唯一目标、相同身份、来源、窗口、Activity、几何和共同露出区域。

- 再次变化就停止；不会反复重试或延长原期限。
- 来源、窗口变化、匹配多个目标、区域不明确等其他证据问题不进入此分支。
- 点击后的预期确认也只重新读取；输入只发送一次，同请求重放不增加读取或输入。
- 取消和超时可中断新增读取。报告保存最终有效的新双帧，不把不一致的旧帧冒充成功证据。

## 验证结果

两个问题均先用旧代码复现，再验证修正。小容量回归使用真实会话、导出和导入：实时报告只保留 3 张图，连续 3 轮、含多个起点条件，旧实现因缺图停止，新实现全部通过。删掉源报告后，各份冻结报告仍可独立打开；32 MiB 默认字节上限未提高。

路径变化测试覆盖一次变化后稳定、持续变化、来源／窗口变化、目标歧义、原期限、取消、点击不重复，以及最终证据实际使用重建后的两个新帧。相关输入、计划、报告、容量和等待测试在原目录最终通过 **151 项／12 文件**，复跑不累加数量。

真机使用原来的 Helper 和同一收藏流程，在一个授权会话内连续执行三轮，没有用每轮换会话避开容量问题。

整批墙钟 173.104 秒，产品耗时合计 153.058 秒。源报告最终占用 30,940,133 字节，默认上限 33,554,432 字节；48 个历史快照带容量裁剪警告，说明本次确实跨过了历史淘汰，而不是只测试低占用状态。

30 份冻结报告、30 个唯一产品步骤均通过官方加载器复核；缺树、缺截图、无效附件和记录错误均为 0。3 次同请求只读恢复、4 次 Helper 自动重读及5 次其他自动重读均保留在耗时中。`absentObservations=9` 是未产出的观察槽位，不是丢失附件；原失败和恢复链都保留，没有补发点击。

本次真机证明了固定业务流程跨容量淘汰后的归档完整性，**没有证明运行中恰好触发过路径变化重建**；后者由原始失败重放和确定性测试验证。此次属于可靠性回归，不是新的速度对照，D6 的 20% 整段提速目标仍未达成。

真机三轮后，归档异常分支又补齐了取消和会话变化的原停止原因保留，并重跑最终 151 项测试及类型检查；成功路径不变，此后没有再次重复真机三轮。
