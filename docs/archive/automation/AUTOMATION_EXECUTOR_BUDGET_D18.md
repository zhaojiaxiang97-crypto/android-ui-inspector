# D18：执行器接入协作式读取预算

更新：2026-10-18。状态：预算接线、本地验证和真机调查完成；三轮连续计划未全部通过，默认关闭。原 Helper 已恢复。

## 改动

[D17](AUTOMATION_COOPERATIVE_READ_D17.md)提供了可取消的设备读取入口，但桌面执行器尚未传入实际剩余时间。D18 将它接到现有观察链路，避免重读时重新取得完整超时额度。

- 会话、整段计划、单步操作和单次采集都记录自己的截止时间。组合时取最早截止时间，使用单调时钟计算剩余时间。
- 动作前读取、动作后读取、双帧确认及恢复读取共用原步骤预算。恢复仍受原来的两次额外读取、15 秒上限约束。
- 发起 Helper 读取前扣除目标窗口、屏幕方向等预检耗时；Helper 会话继续扣除连接和能力协商耗时。
- `ANDROID_UI_INSPECTOR_CONTROLLED_READS=1` 才进入 D17 协议。开关未设置时沿用原读取路径；旧 Helper 只有能力接口明确返回 404 才回退到原 GET。
- 原有授权、窗口遮挡、证据完整性、输入去重和取消判定保持不变。不新增输入重试，不强行释放设备锁。

截止时间附着在进程内的 `AbortSignal` 弱引用表中，不写进外部协议，也不把客户端声称的时间当作可信预算。原生取消信号和超时原因保持原样；没有已知截止时间的调用，仍由单次采集的 30 秒上限约束。

边界夹具验证预检耗时已扣除、后验窗口检查全部结束后才返回或清理；默认模式不传入新协议预算。D17 的真实 HTTP 协议、旧 Helper 回退、取消清理及生产 Java 采集夹具继续通过。

160 项相关测试、类型检查和完整构建通过。这些是正确性验证，不是速度 A/B。

### 容量门槛未通过

第三轮的失败发生在登记保留期内第 33 次受控读取处，与生产控制器的 32 条上限相符。受控读取的桌面错误目前只保留通用 `helper-control`，没有保留底层 `errorCode`，因此该次原始错误不能单独作为容量原因的直接证据。

随后在同一候选 Helper 上，仅发送“取消先到”的登记请求、不发送操作输入，复现登记表满：新的取消和读取均明确返回 `success=false,errorCode=capacity`。原控制器会将终态记录保留到其截止时间后 60 秒；动画恢复会增加登记数量，正常连续计划也可能撞到上限。不能只增加常量或主动删除运行中记录来宣布问题解决。

本轮保留容量拒绝与停止行为，未修改 D17 的防重放和占锁规则。完整连续计划仅 **2/3 通过**，只读恢复通过不能改写成三轮计划全通过。
