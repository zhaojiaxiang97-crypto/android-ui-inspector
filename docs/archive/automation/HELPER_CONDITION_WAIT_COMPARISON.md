# Helper 条件变化与旧版真机对照

2026-10-17，同一手机、同一无 SDK 测试页的新旧 Helper 各三轮只读对照已完成。等待阶段完整观察从每轮 6 次降到 3 次；产品等待中位数从 10546.311 降到 10436.642 毫秒，只差 109.669 毫秒（约 1.04%）。能确认重复完整采集减少，不能据此宣称稳定提速。六轮证据与日志封口审计均通过，原触摸注入失败独立保留。

## 目的与范围

补齐[手机端短时等待](../../HELPER_INPUT_TRANSPORT.md#helper-condition-wait)的动态就绪和旧接口兼容验证。正式对照使用 debug 测试页的固定 Intent 启动 8 秒倒计时，再通过产品只读接口等待；没有在成功样本中发送触摸输入。原触摸实验首轮失败后即停止，没有重发或补样。

测试页在手机上实际运行，经过真实无障碍树、PNG 采集、手机端条件查询及桌面验证链。它用于控制状态变化，不能代表复杂业务页面的读取成本，也不能证明输入权限已恢复。

## 采样方法

1. 固定手机 `DEVICE_SERIAL`、测试页、8 秒延迟、桌面构建与屏幕几何。每个 Helper 的 3 轮共用各自的一个授权会话和服务实例，旧版先测、新版后测。
2. 每个变体用一次 Helper 完整采集预热。每轮再取得一份 Helper 基线完整快照、记录 Activity/进程/焦点身份，仅发送一次固定测试 Intent，再调用一次产品只读 `wait`；产品预算 30 秒，CLI 外层预算 45 秒。
3. `wait` 没有后端参数，继承明确使用 Helper 采集的基线；审计要求所有观察阶段均为 Helper，禁止输入阶段或 UIAutomator dump。每轮新增产品步骤只能是基线采集与只读等待，必须成功、条件已验证、无留证或观察失败。
4. 每轮保存 Intent 准备、基线、等待、授权状态、身份、逐帧审计及报告。计数只能增加 1，失败立即停止，不重发 Intent，也不把原触摸失败改记为成功。
5. 结束旧授权，安装新版，恢复原配对并检查能力；用户对新的服务实例授权后再运行新版 3 轮。

新版本必须实际取得一次触发后的未就绪完整观察，再得到 `ready` 提示，随后取得两份唯一 ready 可见的全新完整观察；仅走“已满足”路径的轮次不计为动态覆盖。旧版要求首轮只有一次 404 探测，后两轮同服务不再探测等待接口，继续使用 Helper 完整观察。

## 有界诊断与证据

产品报告保留步骤前后证据，未保留全部中间帧。因此本轮增加临时、私有的 fetch 诊断，仅在测试用 Electron 主进程运行；没有新增公共接口、额外设备请求或产品配置。

诊断只记录固定测试包的服务、窗口、显示器、capture ID、单调时间、ready 可见匹配数和数字运行计数；等待响应只保留允许的提示字段与 HTTP 状态。它不保存请求头、配对令牌、原始正文、XML 或 PNG。最多 512 条、2 MiB，缺口、溢出和未完成退出均明确标记，并使样本审计失败。

hook 保留原 fetch 参数、signal、Promise 和 Response。异步克隆、JSON/XML 解析与写入仍会消耗主进程资源。两套 APK 使用同一 hook；以下数据属于“开启同一私有诊断的样本耗时”，不能当作无诊断的稳定性能结论。

审计使用请求序号和设备单调时钟，不依赖异步写入顺序。需要核对最后 ready 提示与后续两份 capture 的时间水位、不同 capture ID、相同服务/窗口/几何、完整状态和唯一 ready 匹配；原始诊断必须由原 hook 在真实退出时产生唯一、位于末尾的完整 footer，不能事后补写。

私有 runner、诊断、自检与原始结果位于主工作树忽略目录 `.benchmarks/device-wait-transition/`。诊断 mock 自检、12 个审计场景自检及独立审查已通过，测试没有放宽现有授权、来源、唯一目标或区域检查。

## 原触摸实验的失败边界

2026-10-17：旧版已获得测试应用授权，但第一轮在触摸输入阶段失败，脚本立即停止，没有重发或补样。产品整步 1983.450 毫秒，CLI 墙钟 2118.537 毫秒；这些是失败耗时，不是等待性能数据。

输入命令返回 exit 0 且无输出，但 Android 的 UID 1000 / system_server PID 1582 在该请求的 151 毫秒设备时间窗口内，明确记录输入 PID 15779 注入失败。相邻日志显示 MIUIInput 收到 DOWN/UP、InputDispatcher 丢弃 UP。现有证据无法进一步确认系统拒绝的具体原因，不能直接归因为某个设置。

产品将结果标为 `injection-failed / unknown / verified=false`，保留请求 `68cfa6a8-632f-4403-9523-7582494b441e`。一次额外只读采集确认测试页运行计数仍为 0、ready 匹配数为 0；手机处于 Awake。没有调用恢复步骤，也没有再次输入。本轮只有预热、动作前及失败后的三份完整快照，没有等待接口请求或 404，成功对照样本为 0。

因此后续采用独立的只读动态实验：仅 debug 测试页通过固定显式 Intent 启动倒计时，产品仍通过原授权接口读取和等待。每轮核对进程、Activity、窗口、服务和计数。这只是测试状态准备，不属于产品输入成功，也不修复上述系统输入失败；两类实验分别记录。

切换 Helper 会重建无障碍服务，桌面原授权仍绑定旧 `serviceInstanceId`，必须结束旧会话并重新人工授权。这是[现有会话归属检查](../../../electron/capture/helper-session.ts)的要求，不会为对照测试绕过。

## 调试夹具与只读约束

为了单独验证条件等待，debug Activity 增加固定 action `com.androiduiinspector.sdkfree.RUN_DELAY`，仅在 `singleTop` 复用已有 Activity 的 `onNewIntent` 中启动倒计时。首次创建页面不会触发该 action；如果系统意外重建实例，计数不会增加，审计必须拒绝。按钮仍可手动使用，延迟仍限制为 2000–20000 毫秒。release 中没有此 Activity、action 或对应资源，没有新增权限。

每轮先经产品接口取得 Helper 基线完整快照，再执行一次显式 Intent 准备测试状态，随后调用原有只读 `wait`。Intent 前后必须保持相同进程、Activity 和焦点窗口，帧内服务、窗口与几何也必须一致；计数只能从 N 变为 N+1。Intent 不算产品输入，没有失败重发。每轮只有基线、触发后的 false 帧和后续完整 ready 帧符合审计，才收为动态条件样本；任何已就绪快路、身份变化或留证缺口都会停止该轮。

这组实验与原触摸实验分开保存。基线采集、Intent 准备及产品等待分别计时；对比的是相同已开始计时条件下的等待成本，不能据此宣称自动点击已通过。新旧版六轮都保持了相同进程、Activity 记录、组件和焦点窗口。

私有脚本 `run-readonly-variant.mjs` 已通过语法检查、身份与只读守卫自检及独立复审。首次会话在预热前允许报告路径为空；预热后重新核对同一会话、设备、包与到期时间，并固定有效报告路径。六轮实际结果均经独立重算，最终完整 footer 与产品报告附件也已核对。

## 结果解释

每个变体仅 3 轮，按原值、中位数和最大值报告，不计算 P95。产品整步、CLI 墙钟、完整观察与短时查询分别计时，嵌套阶段取时间并集；8 秒测试页定时属于固定业务等待。旧版先测、新版后测存在顺序偏差，多设备和复杂业务页仍需后续验证。
