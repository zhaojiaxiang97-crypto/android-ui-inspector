# 采集内部耗时拆解（阶段 D2）

更新：2026-10-17。D2 已实现并完成真机完整流程验证，23 次实际采集请求全部取得合法细分计时。桌面 162 项测试、手机端 18 项测试、类型检查和构建通过。本轮定位出 JSON 序列化这一明确开销，不把增加计时当作提速。

## 要回答的问题

[D1 完整流程](AUTOMATION_TIMING_PROFILE.md)的 23 次采集，树读取合计 14.952 秒、PNG 编码 6.239 秒。主机等待采集响应头共 32.316 秒，比手机观察总计 24.997 秒多 7.319 秒。

本轮区分树中的节点访问与本地处理，并直接测量返回响应前的调度和编码。原有采集范围、图片格式、输入、恢复和来源校验不变。

## 计时边界

仅已鉴权的 `GET /inspector/snapshot` 响应增加 `X-Inspector-Snapshot-Timing`。旧 JSON 协议不变。响应正文只进行一次 JSON 序列化和一次 UTF-8 编码，编码结果直接发送；不会为填计时字段重复生成正文。

| 字段 | 表示什么 | 包含关系 |
| --- | --- | --- |
| `queueMs` | socket 接收后提交工作线程，到线程开始执行 | 不是采集锁排队；采集锁仍立即成功或拒绝 |
| `preObservationMs` | 工作线程开始到进入采集调用 | 包括请求读取和鉴权，不等于 CPU 时间 |
| `observationMs` | 完整采集函数调用 | 包含原 JSON 中设备观察计时及少量入口、返回工作 |
| `jsonSerializationMs` | 正文 JSON 序列化 | 在采集调用之后 |
| `utf8EncodingMs` | 正文 UTF-8 编码 | 在 JSON 序列化之后 |
| `cacheClearMs` | 清除无障碍缓存 | 在采集内；系统不支持或未执行则缺失 |
| `initialWindowReadMs` | 前置屏幕信息和窗口枚举 | 在采集内、树遍历前 |
| `getChildMs` | 全部节点 `getChild` 调用累计 | 在树遍历内，不推断为纯 Binder 时间 |
| `nodeLocalMs` | 本节点属性读取、裁剪、XML 构建及回收 | 不重复累计子节点访问和递归，不等于纯 CPU 时间 |

节点耗时先用单调时钟纳秒累加，最后统一换算为毫秒，避免每个节点取整丢失小耗时。所有字段只含固定名称和有界数字，不包含页面内容或身份。

## 兼容与统计

- 独立响应头缺失、超长、格式错误、重复字段或未知字段时，不记录新增诊断；原采集仍按原规则验收。
- 报告仅在采集端点的响应头阶段保存新增计时，并深复制嵌套数据；旧报告可继续读取。
- 按原步骤和父观察关系分为普通读取、自动重读、独立恢复。失败尝试仍保留合法诊断，不能因此变成成功。
- 前五项互不重叠，可算已测服务器处理小计。树子项已包含在观察中，不能再次相加。
- 主机响应头时间减去服务器小计，以及服务器采集时间减去旧观察时间，都保留有符号差额。时钟和取整误差可能产生小负数，不截断成零，也不命名为纯网络耗时。
- 旧数据或没有执行的阶段以缺失次数、空均值表示，不补零。保留快照与逐次尝试仍是两组独立统计。

## 验证记录

新版 Helper 已安装，签名与原版一致；原配置启动新版桌面。首次起点读取遇到 Helper 更新清空内存配对后的 HTTP 401，未发送任何输入，失败归档单独保留。结束该会话、恢复原配对并验证能力接口返回 200 后，重新授权同设备和同 Debug App，运行完整业务流程。

“播放起点 → 返回 → 我 → 收藏 → 严格末端 → 最后有效视频 → 播放状态确认” **1/1 通过**：墙钟 68.641 秒、产品耗时 62.921 秒，6 次唯一确认输入、0 次未知输入。保存 8 份冻结归档、10 个唯一步骤。42 个附件（21 树、21 图）的摘要、长度及独立导入均通过；末端双帧、末卡和最终播放语义通过。3 个未产出观察槽位由原失败及恢复链解释，未作为附件缺失放行。播放确认仍是业务语义校验，不是解码质量或实际播放进度测试。

普通读取 20 次、自动重读 1 次、独立恢复 2 次，共 **23/23 次**实际采集请求均有合法响应头，并准确关联同一次设备观察；其中一次失败且声明不完整的采集也保留计时。独立审计逐项重算新统计，与离线汇总完全一致。

### 本轮 23 次请求的累计结果

| 服务器阶段 | 累计耗时 |
| --- | ---: |
| 工作线程调度 | 0.011 秒 |
| HTTP 读取、鉴权等前置工作 | 0.043 秒 |
| 完整采集调用 | 28.657 秒 |
| JSON 序列化 | **7.685 秒** |
| UTF-8 编码 | 0.227 秒 |
| 以上五项合计 | 36.624 秒 |
| 主机等待响应头 | 36.938 秒 |
| 尚未归属的响应头差额 | 0.314 秒 |

原设备观察计时合计为 28.620 秒，比主机响应头时间少 **8.318 秒**。其中 JSON 序列化直接测得 7.685 秒，占这个差额的 **92.4%**；UTF-8、调度、请求前序和采集入口/返回差额另外解释了约 0.319 秒。最后 0.314 秒仍保持未归属，不能直接命名为纯网络传输时间。这是本轮数据的归因，不能把它回填成旧 D1 样本的精确成因。

| 采集内阶段 | 累计耗时 | 说明 |
| --- | ---: | --- |

| 前置显示信息与窗口、根节点读取 | 1.056 秒 | 包含独立恢复中的一次 0.336 秒读取 |

本轮全流程比 D1 单轮耗时更长。两次的页面动态内容、首轮调度及恢复过程并非受控性能实验，因此不据此断言诊断带来多少开销，也不宣称提速。下一轮要在同条件前后对照中验证改动收益。

## 后续决策

优先验证 **JSON 响应序列化**：本轮直接测到 7.685 秒成本，边界集中，通常比改变节点预取和跨进程读取更容易保持现有行为。先做代表性响应的可重复编码对照，核对解析后的所有字段、PNG 字节、Unicode／转义字符、错误响应及 Content-Length；验证通过后再做完整流程同条件对照。不能为了快而删除树字段、降图像质量或放宽完整性校验。

官方 Android 14 参考实现中，[JSONObject.toString/writeTo](https://android.googlesource.com/platform/libcore/+/refs/tags/android-14.0.0_r1/json/src/main/java/org/json/JSONObject.java#699)遍历字段，再交给 [JSONStringer.string](https://android.googlesource.com/platform/libcore/+/refs/tags/android-14.0.0_r1/json/src/main/java/org/json/JSONStringer.java#312)逐字符处理字符串，包括对 `/` 的转义。大 Base64 字符串也经过这条路径，存在逐字符处理及缓冲增长成本。这是候选机制的源码依据，不是当前厂商 ROM 的函数级采样；7.685 秒还包含 XML 和其他字段，不能全部归给 Base64。

随后交付的 [D3 JSON 输出优化](HELPER_JSON_SERIALIZATION.md)已实现此候选：不修改原 JSONObject，浅复制除 `screenshot_base64` 外的字段，继续用原 JSON 序列化器处理这个对象；对确认合法且有界的 Base64，预分配缓冲后批量追加固定字段与字符串，最后仍只做一次 UTF-8 转换。非字符串、无图、空、非法或超限 Base64 走原路径，不修复输入。JSON 字段顺序和可选斜线转义允许不同，解析后的所有值与 PNG 字节必须相同。

候选验证必须覆盖：原对象及嵌套字段不变；Base64 的 `/`、`+`、填充和非法字符；中文、emoji、引号、反斜线及控制字符；失败和不完整响应；独立解析后逐字段等价、PNG 摘要／尺寸／透明度及 UTF-8 Content-Length；大图上限、长度溢出和峰值内存。校验、复制和拼装全部计入序列化时间，不能隐去新增开销。先做同机固定响应的配对微基准，再跑完整流程及证据回归。

D3 的同机固定数据对照已完成：常见图片档 JSON 编码中位耗时下降约 73%–77%，近上限压力响应也通过；工程共 186 项相关测试通过。新版完整业务 1/1 通过，墙钟 66.274 秒、产品 60.063 秒，6 次确认输入、0 次未知输入。同日原版为 66.361／60.456 秒，整段耗时基本不变；该单轮不是同条件性能验收，完整结果及失败记录见 D3 文档。

节点访问占 D2 树读取 77.1%，是下一步调查的方向；需要进一步区分预取、应用节点提供器和窗口变化，不能只凭累计耗时替换预取策略。线程调度和清缓存目前成本很小，不优先改动。

完整任务提速仍按[阶段 D 验收](../../AUTOMATION_NEXT_STEPS.md)做同条件对照。当前诊断样本用于定位，不作为已达到 20% 提速目标的证据。
