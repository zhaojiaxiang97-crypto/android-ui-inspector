# D21：同版本读取协议速度对照

更新：2026-10-18。结论：本轮未证明协作式读取能加快完整导航流程，继续默认关闭；20% 整段提速目标仍未达成。本轮没有修改生产代码。

## 对照条件

使用同一工作树构建、同一候选 Helper APK 和同一 Helper 服务实例，仅通过重启桌面切换读取开关。A 为默认 GET，B 为显式开启 `ANDROID_UI_INSPECTOR_CONTROLLED_READS=1`。Helper 在四组之间未重装或重启，各报告的服务身份一致。

固定设备 DEVICE_SERIAL、自有 Debug App `com.androiduiinspector.sdkfree`。流程为进入真实子 Activity，再返回并确认计数；开始和最终页面均需验证。采用 A→B→B→A，每组三轮，每组新授权、重置测试页计数；输入方式、条件、时间预算及轮询间隔相同。每轮前后检查横屏 `lock 3`，每张已接受快照核对 2400×1080、rotation=3。

每组首次运行与后续运行分列。“首次”指该桌面会话的第一轮，不是清缓存后的严格冷启动。墙钟包含计划提交、CLI 和每 500ms 状态轮询；产品耗时取 `run.durationMs`，不含外部轮询延迟。桌面启动、授权和报告复核另计，不混入单次流程。

## 失败与排除记录

正式 3-B 首轮进入子页成功，返回回执确认发送；之后读取报“无法确认前台 App”，计划停止。仅调用原 requestId 的只读恢复，取得完整观察并确认返回；没有重发返回、没有继续原计划，原失败状态保留。恢复后的附件单独保留在同一组报告中，恢复耗时不计成功流程。

源码 `electron/device/target.ts` 中，该错误把活动查询命令失败、没有解析到前台目标、包名无效合并成同一消息。本次报告不足以区分是哪一种，不能断言是协作式协议造成，也不能因为稍后恢复成功就把原失败改成通过。本轮固定版本对照期间不修改此逻辑。

正式对照前还有两个完整保留的预检组：原 1-A 横屏三轮通过，原 2-B 首轮竖屏采集失败，方向回读为 `lock 0`，与 A 条件不同。B 点击已发送，只读恢复确认进入子页，未执行返回和剩余两轮。这两组整体排除出速度统计，保存在 `preflight/`；方向变化原因未定位，不猜测为协议导致。正式批次将方向设置放在测试页重置之后，并逐轮核对，没有方向不一致。
