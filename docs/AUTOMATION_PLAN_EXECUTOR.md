# 操作计划执行器

AI 一次提交结构化计划，桌面持续执行并验证；普通步骤无需再次调用 AI。异常时停止，返回原请求编号、停止原因和证据位置。计划执行器在桌面进程内运行，不要求被测 App 引入 SDK。可选 Helper 的后续[短时条件等待](HELPER_INPUT_TRANSPORT.md#helper-condition-wait)只提供调度提示，最终结果仍由桌面完整观察确认。

## 使用

先在桌面为指定设备和 Debug App 开启自动调试。在“更多工具 → 自动调试 → 操作计划”粘贴计划 JSON，点击“校验计划”和“运行计划”。界面显示当前步骤、已跳过或失败的步骤；“取消计划”只取消本次计划，原“停止”按钮仍会撤销整个会话授权。

AI 或脚本也可通过 CLI 提交：

```sh
node dist-electron/cli.cjs attach
node dist-electron/cli.cjs plan-start --session '<当前会话UUID>' --run-id '<调用方预先生成的UUID>' --plan-file /绝对路径/plan.json
node dist-electron/cli.cjs plan-status --session '<当前会话UUID>' --run-id '<同一个UUID>'
node dist-electron/cli.cjs plan-cancel --session '<当前会话UUID>' --run-id '<同一个UUID>'
```

`plan-start` 只返回接收状态，计划在桌面后台继续执行，不等待全部完成。CLI 退出或接收回执丢失不会取消已经接受的计划。MCP 对应工具为 `start_debug_plan`、`get_debug_plan`、`cancel_debug_plan`，与界面和 CLI 共用同一个执行器。

响应丢失后查询原 `run-id`。同编号、同参数再次提交只返回原运行；改变参数会拒绝。尚未查询到原运行时，也不能换编号盲目重发。撤销授权后会关闭原桥接服务，不能保证 CLI/MCP 仍能查询；可查看桌面尚保留的会话或本地计划记录。退出桌面不会自动恢复计划。

## 计划格式

可从[示例 JSON](../scripts/fixtures/automation-plan.example.json)开始，将示例包名和控件条件替换为实际 Debug App 中唯一、稳定的选择器。示例不会自动启动 App 或授权。

| 字段 | 含义 |
| --- | --- |
| `version`、`title` | 固定版本1与计划名称 |
| `backend` | 整段计划固定 `uiautomator` 或 `accessibility-helper`，默认前者 |
| `timeoutMs` | 整段计划总时限，1秒至10分钟，默认5分钟；授权须另外留出1.5秒收尾余量 |
| `startConditions` | 开始前用两次新观察检查的条件，1至5个 |
| `steps` | 顺序执行的1至32个步骤，步骤编号必须唯一 |
| `finalConditions` | 步骤完成后再次独立检查的条件，1至5个 |

定义按 UTF-8 最多12000字节；CLI 文件和界面输入也有此大小限制。每个会话最多接受10份不同计划。计划不能传入任意命令、代码、坐标、外部文件路径或伪造的视觉确认，也不能自行切换授权 App。

步骤有三种：

- `kind: "step"`：`input` 沿用现有单步的 `target`、`action`、`expect`、`timeoutMs`。支持点击、返回和单次滚动；`expect` 必填。会话、子请求编号和后端由执行器固定。
- `kind: "scroll-until"`：`input` 沿用现有连续滚动参数，每次动作重新校验，最多12次。明确终点或目标双帧确认才通过；无进展和次数用尽都不算到底。
- `kind: "wait"`：提供 `condition: {selector, state}` 和最多30秒的 `timeoutMs`，只观察、不输入。

连续滚动可显式设置 `inputMethod: "accessibility"`：仅限 Helper 后端、纵向、包含资源 ID 和类名的唯一可滚动容器，手机端须暴露对应滚动动作；不能使用视觉确认兜底。缺省仍为手势，发送前确定方式，失败不换通道。固定 24 项列表的三轮结果及可运行计划见[阶段 B 验收](archive/automation/HELPER_SCROLL_STAGE_B.md)。

任一步骤可增加 `when: {selector, state}`。两次新观察均不满足才跳过；条件不稳定、定位歧义或证据不足会停止，不把读取失败当作条件为假。第一版采用有限条件跳过，没有任意表达式、递归或无界循环。

条件的 `state` 为 `visible / absent / enabled / disabled`。计划内部的等待与操作后验证采用严格双帧检查：可见控件必须唯一，“不存在”需要完整控件树；普通单步接口保留原兼容行为。

## 执行与记录

整段计划持续占用调试会话。外部点击、采集、等待和任务验收不能插入；查询、取消计划和停止会话继续可用。计划不会占用或覆盖已有 `debug-task` 定义，它有自己的起点、条件和最终检查。

接受计划时先保存定义摘要、运行编号和全部子请求编号；每次实际输入前核对授权、取消信号和记录完整性。记录丢失、被改动或无法读取时禁止下一次输入，连续滚动中的下一次动作也会被拦住。输入结果未知时不重发，不自动切换路线，也不自动恢复观察后继续后面的动作。

取消会阻止后续操作，并等待当前步骤收尾后释放占用。已经发出的触摸不能撤回；取消回执仍显示运行中时，应等待后续状态更新或查询原编号。

返回状态包含 `run.status`、逐步结果、实际产品步骤编号、总耗时、`reportPath` 和 `ledgerPath`。操作及观察进入现有 `report.json`；计划定义和整段结果单独保存在会话私有目录的 `plan-<runId>.json`。当前报告导出不会自动把这份计划记录打包进去，分享计划时需单独检查并附上该文件。

现有报告容量限制仍生效，较长计划可能裁剪早期截图或控件树。`passed` 表示运行时声明条件验证通过，不承诺所有历史附件完整，也不代表自然语言目标中的任意业务副作用已被证明。

## 本版边界

- 已实现桌面自动执行、CLI/MCP/界面入口、有限条件跳过、严格验证、独占、取消及持久编号。
- 手机端计划解释器、动态“最后一项”目标和自动 AI 修复后续计划尚未实现。当前目标仍使用精确选择器，未知状态返回调用方处理。
- 进入播放器页面不等于证明视频已开始播放；需要额外声明可观测的播放状态或进度条件。
- 本版减少逐步模型调用和命令入口往返，不自动消除设备采集耗时，也没有宣称解决此前系统输入拒绝。真实端到端提速仍需同机对照。

设计背景见[方案建议](archive/automation/AUTOMATION_PLAN_EXECUTOR_PROPOSAL.md)，既有回测工具见[多轮回测](AUTOMATION_UI_REGRESSION.md)。
