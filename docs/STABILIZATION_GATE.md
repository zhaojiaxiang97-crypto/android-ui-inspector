## 可靠性指标与扫描成本

本轮新增 [可靠性汇总](../scripts/regression-quality.ts)，以 `summary.json` 为输入。统一计算任务完整成功率、首次成功的单轮墙钟、首次动作成功率、超时轮数/比率、未知派发轮数及有证据的下界、自动重读/独立只读恢复次数。缺失的“业务重复动作数”和“恢复墙钟”保留为 `null`，不能假造为零。不同计划 SHA、不同后端及不同候选禁止混用；汇总前还需人工对照机型、App 内容和 APK 摘要。

`bun scripts/regression-quality.ts diagnosis-handoff-20261018-f881f360 3` 对 D24 正式三轮输出：计划 3、已执行 0、待执行 3、任务成功率 `null`。只有实际产生的报告才进入分母，真实耗时包括恢复和报错分支；“输入回执 `sent`”不足以宣布业务成功。

本轮 [只读扫描分析](../scripts/analyze-target-scan.ts)使用 D24 `.benchmarks/d24-target-probe/readonly-scan-20261018.json` 的原始诊断：750 节点、截止时 428 节点访问、427 次完成子读取累计 794 ms，扫描时段 948 ms。在“同一窗口、静态树、剩余节点读取成本与已完成读取均值相近”的假设下，完整扫描估算约 1547 ms，均次子读取要从约 1.86 ms 降至约 1.06 ms（约 43%）才能留在当次扫描余量内。**这是单样本建模，不是无法在 1 秒完成的证明，更不是缓存优化已生效。**

后续只读采样按 100 / 300 / 500 / 750 / 1000 节点分组，分别报告冷/热读、树深度、完成与未完成的子读取、诊断负担及 P50/P95（足够样本量后）。只有掌握同样正确性约束下的成本证据，才选择缓存、预检结构或验证流程调整。

## 独立设备验收步骤（人工启动）

1. 固定可复现源码，保存 `candidate.json`、构建哈希、桌面/Helper 的实际已安装 SHA、协议版本、能力协商和当前配对状态。设备和 App 必须是自有样例或当前任务明确授权的复杂页面。
2. 设备在线、焦点/窗口/分辨率和 Helper 配对均通过后，在桌面由用户显式授权。先做有限只读扫描，验证未发输入，原始失败和超时留证且没有积压的旧任务。
3. 在同一冻结候选和固定计划上执行完整业务三轮（成功、超时、未知需全部留证）；每轮新 `requestId`，响应丢失只查原 ID 或恢复观察，**不得自动补发可能已经执行的输入**。
4. 逐轮核对动作次数、首次成功耗时、超时/未知、恢复及证据目录，结束时确认授权、会话、转发和进程清理；失效或版本不一致应标记阻断，不将结果算入稳定成功率。
5. 对照同一个 frozen candidate 的 CI 与设备证据，只有确认通过才进入安装版升级/发布审核。目前此轮尚未经过设备验收。
