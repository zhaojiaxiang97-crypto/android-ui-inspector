## 复核后采纳的结论

现有证据仅证明：750 节点页面的输入前核对在 37 ms 进入 `target_scan`，1004 ms 超时且未发送。根预取标志调整也失败并已撤回。扫描内具体慢调用尚未确认。

下一步应补一份请求独立、可在超时线程读取的扫描诊断，区分“一个子节点读取阻塞”和“许多短调用累积”。诊断保持小型固定结构，至少包括：已检查节点数、已开始与已完成的子节点读取次数、当前操作及其开始时间、已完成子读取的累计及最大耗时。操作仅用固定枚举，不包含节点正文、资源 ID、类名、路径或异常文本。

诊断状态必须在阻塞调用前发布；超时生成回执时一次性冻结一致快照，之后不得被迟到的主线程修改。只在 `timeout / not_sent` 且主线程已开始、确已进入扫描时附加。时间使用同一单调时钟，计数受现有遍历上限约束；越界数据拒绝或省略，不伪装成有效测量。旧回执可不带此对象，新字段及严格校验须与桌面解析同步交付。

不改变 1 秒发送前期限、完整树唯一性、精确元组、窗口与新鲜度核对、一次性凭据、CAS 和失败停机规则。诊断不能参与授权或派发决策。

## 未采纳的建议与原因

- 不能把每次 `getChild` 都当作一次 IPC，更不能把 `getBoundsInScreen`、`getChildCount` 直接当成远端查询。节点缓存和本地字段会影响成本；当前没有逐调用实测。
- 不能仅在异常返回时附加诊断。阻塞读取可能晚于截止时间返回，而超时回执已生成，这会丢掉最关键的现场。
- 不新增重复匹配“抑制”计数等无关字段。重复目标现有行为是立即拒绝；本轮只需定位耗时。
- 不将耗时强行截成 3500 ms，截断会掩盖真实迟到。应记录回执冻结时可观察到的时长，并严格约束时间关系。
- 不采纳“旧回执省略 method 也应由 HTTP 客户端接受”。`electron/capture/helper-input.ts` 明确要求执行方式匹配；可选诊断字段不应放宽此检查。
- 不采纳把子节点预取标志改成 8 的测试。撤回的是根节点 8→40 的候选；子节点原本就是 40。
- 不接受“750 个近似目标必须拒绝”或“发现重复后仍遍历全部节点”的断言。近似目标不等于重复，确认歧义时可立即拒绝；唯一有效目标必须在完整扫描后才获准派发。
