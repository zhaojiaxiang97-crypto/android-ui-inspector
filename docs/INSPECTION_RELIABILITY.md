日期：2026-09-22。沿用 Electron + React + WebGL，不引入新的运行依赖。

## 本次改动

- 打包不自动发布；Windows 不再依赖未下载的 Electron 目录；Linux CI 正确配置沙箱，补齐包维护者与项目主页。CI 显式使用 Node 22。
- 原生采集按窗口根控件身份匹配目标窗口，不再默认取第一个窗口。同名同矩形或重复位图标记为歧义，不再用遍历顺序猜对应关系。
- 节点显示独立画面的采集状态，缺失不伪装成透明；采集警告不再被样式隐藏。
- 同级实测 Z、绘制顺序和索引共用排序规则。收起时仅合成本分支独立位图，支持已暴露的矩形裁剪、padding 和分组透明度，不把有效 alpha 重复叠到每张子图上。
- 显示采集阶段、用时并允许取消；取消/返回/切换设备后旧结果失效，关闭连接并清理本次端口。新采集等待旧调试会话释放。
- 快照记录阶段耗时；PNG 压缩改为异步；只为当前可见层准备纹理，串行解码，移除不再需要的纹理。图层 GPU 纹理预算约 64 MB（不含基础截图、画布和驱动开销），单图最多 200 万像素，超预算缩小纹理而不删除节点。
- 展示层数上限仍为 512；会提示省略数量，选中上限之外的节点仍可定位。首次采集依然默认展开全部分支。

## QML 背景丢失修复（2026-09-22）

现场对照：2D 有卡片底色，展开后的 `QQuickRectangle` 却只有轮廓。原采集只读取几何和文本，缺少样式；没有独立画面的父节点又被当作纯结构层。

本次沿用现有纹理通道，不新增依赖：

- 从目标对象读取实际 RGBA、边框宽度/颜色、四角半径、水平/垂直渐变，以及 clip、有效透明度和 layer.enabled；不把文本颜色当背景色。
- 在本地生成只包含该节点自身样式的透明 SVG；不裁切整屏图片，不复制子节点的像素。图片尺寸沿用纹理预算。
- 即使 Rectangle 有子节点，也显示自己的样式。纯容器没有自身样式时保留轮廓。非视觉对象和零尺寸包装节点不再误挡住可见后代。
- 折叠使用同一份自身图层合成子树；QML 默认逐项透明度、layer.enabled 分组透明度和负 Z 子节点分别处理。选择仅改变高亮，不改变纹理。
- 属性栏明确显示“QML 真实样式重建（非独立截图）”，并展示背景色、边框和圆角。

边界：本次不是完整 Qt 渲染器。渐变预设、ShaderEffect、任意变换、复杂文字/图片/自绘内容不能保证重建；缺失内容不代表透明。其他旧叶节点截图近似仍保留，因此折叠合成暂不等于完整页面截图。旧快照没有新增属性，需要重新采集。

Qt 默认 QQuickPen 会返回黑色/1px，但其内部启用状态不通过 QML 属性暴露。这一歧义组合不擅自画黑边，属性栏保留实测值并提示边框状态；明确指定为相同默认值的真实黑边也暂时省略。非默认颜色/宽度的边框正常重建。

验证：新增采集表达式、颜色解析、非视觉包装、负 Z、样式纹理单测；新增真实 Canvas/WebGL 像素检查，覆盖颜色/圆角/边框/透明度/裁剪和展开→折叠→再展开。

- 单测 83 项通过；100%/125%/150% 页面缩放各 32 组坐标及像素检查通过，其中 7 组是图层像素检查；三档 DPI 代理及树交互回归通过。
- macOS arm64 重新打包并启动，在连接的 Android 真机上重新采集 `com.reclip.videodownloader.dev`。调试读取获得 141 个背景样式（含隐藏项）。
- 实际界面中选中 `mobilePreviewPlaceholder`：背景为 `rgba(33,29,30,1)`，边框为 `rgba(75,69,70,1)`，四角半径为 56.25 屏幕像素。卡片已显示底色，属性栏来源标识正确。
- 在运行的打包版中执行全部折叠，再全部展开：背景色与圆角都保留，没有恢复成空白父层。折叠图仅合成已支持的样式，未声称补齐缺失文字或复杂自绘图像。
- 已清除临时搜索、恢复展开视图，程序保持打开。本次未提交或推送 GitHub。

语义参考 [Qt Rectangle](https://doc.qt.io/qt-6/qml-qtquick-rectangle.html)、[Qt Gradient](https://doc.qt.io/qt-6/qml-qtquick-gradient.html) 和 [Qt Item 的透明度与图层](https://doc.qt.io/qt-6/qml-qtquick-item.html#layer-opacity-vs-item-opacity)。

## 原生 Debug App 根窗口匹配修复计划（2026-09-22）

现场：`com.smile.gifmaker` 已通过 Debug 检查，读取到 1230 个控件，但所有独立画面采集被“Debug 窗口与当前控件树不一致”中断。

原因：Activity 输出的根节点是 `DecorView@9c5dabe[HomeActivity]`，没有普通 View 的大括号和坐标，旧解析器跳过了它。随后把其子节点 `LinearLayout@65440cf` 当成根去匹配，而调试接口返回的是 `com.android.internal.policy.DecorView@9c5dabe`。设备同时有两个窗口，不能直接改回“取第一个窗口”。

### 执行顺序

1. 保留简写的 DecorView 根节点及对象身份；没有读取到的尺寸先留空，再由调试属性补齐，不用 App 区域假装真实窗口尺寸。
2. 仅兼容 DecorView 的简写/完整类名差异，仍要求对象身份一致且窗口唯一；匹配成功后补齐完整类名，沿用现有属性和独立位图流程。
3. 补回归测试：真实格式的根节点、父子关系、尺寸补齐、多窗口正确选择、错误身份拒绝、多个匹配拒绝；原有标准 View 格式保持兼容。
4. 执行单测与构建，再重新打包启动，用当前真机验证不再出现根窗口不匹配，且实际取得独立图层画面。

### 范围

不修改手机 App，不新增依赖，不重写渲染器，不放宽同名位图的歧义检查。自定义 `toString()` 导致的其他节点缺失、SurfaceView 视频画面等限制单独记录，不把根窗口修复宣称为所有控件完整支持。

### 执行结果

- 根节点保留、简写身份匹配、完整类名及实测尺寸补齐已实现；普通 View 格式不变，重复匹配仍拒绝。
- 85 项单测通过，0 失败；类型检查、生产构建、macOS arm64 打包通过。
- 当前真机 `com.smile.gifmaker`：1231 个节点（比旧版多出原先丢失的 DecorView），成功匹配 `DecorView@9c5dabe`，读取根窗口真实尺寸 1080×2400，获得 148 张独立图层图片，采集约 29 秒。
- 此次还有 4 个歧义节点、318 个未获得独立图片的可见节点、760 个隐藏节点。这些计数随页面变化；没有宣称所有节点画面均已支持。
- 打包版已重启并重新采集，界面显示 1231 个节点；切到 3D 后可见白色背景、文字和红色按钮等独立画面。选中 DecorView，属性栏显示“已采集独立画面”，尺寸 1080×2400、对象身份与真机一致。旧窗口不匹配错误已消失，仅保留 4 个歧义节点提示。

## 自定义控件与歧义图层补齐

本轮现场诊断：Android 已返回 757 条图层记录，其中 252 张可见图片，但旧树只能对应 158 张；DDMS 树中另外存在 104 个旧树遗漏的节点，主要是覆盖了 `toString()` 的自定义图片控件。很多无位图的 FrameLayout 则是系统跳过自身绘制的纯容器，不能当成缺失背景。

实施方式：

1. 确认根窗口后，用已有 DDMS 对象树恢复真实父子关系、完整类名、资源 ID、尺寸及可见性；Activity 文本只负责先定位根窗口。
2. 继续优先使用系统批量独立图层。剩余同名/同位置、以及可绘制但未匹配的节点，复用 JDWP 通道按对象身份读取自身快照，明确排除子节点内容；不拿整屏截图或包含子树的截图冒充自身画面。
3. 保留超时、取消、逐对象资源释放和数量/像素限制；单个对象失败不丢失其余已采集结果。纯容器明确提示，不伪造颜色。
4. 补树恢复、位图身份、子树隔离与失败清理回归，并在当前真机验证。

参考：[AOSP ViewDebug](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/core/java/android/view/ViewDebug.java)。其批量图层排除子节点、普通单 View 截图包含子节点，两者不能混用。SurfaceView 视频是独立 Surface，仍需单独验证，不能用视频后方的截图替代。

实现与验证：

- 已恢复 DDMS 完整对象树及遗漏的自定义节点，保留原有资源 ID；新增节点只显示系统实际返回的资源名，不猜测资源命名空间。批量图片从窗口坐标换算到屏幕坐标，避免有窗口偏移时匹配失败。
- 自绘 View 使用系统 `createSnapshot(..., skipChildren=true)`；TextureView 沿用自身 `getBitmap()`。不读取父层或整屏图片来填充子层。ViewGroup 没有自身绘制时保留透明/轮廓，并在属性栏说明原因。
- 补采通过已确认的窗口名和完整对象身份定位，不遍历整个进程堆；在 `MessageQueue.next()` 的消息边界暂停主线程，不在绘制/布局过程中单步插入采集。结束或失败均释放对象引用、临时位图和调试会话。
- 补采限制为每次 64 个节点、每张 400 万像素、整段最多 15 秒；时间/数量上限或单节点失败在属性栏说明，已得到的图片保留。窗口身份变化则拒绝补采，尺寸变化的位图也不会拉伸贴给旧节点。首轮打包验收发现当前页有 34 个补采对象，原 32 个上限会遗漏头像，因此调整到 64。
- 同一真机页面恢复了 104 个节点，旧树遗漏的自定义图片中有 22 张获得了匹配；现场完整采集曾得到 1335 个节点、186 张独立图片，其中 16 张来自按对象身份补采。页面和可见状态变化会影响数量，不能与另一页面直接比较。
- 最终窗口直查方式对同一组 `KwaiImageView` 和 `CheckedTextView` 的补采耗时约 1.4 秒，原堆扫描方式约 8 秒。这不是整个页面的采集耗时。
- 87 项单测通过，覆盖遗漏自定义父子节点、真实属性、窗口偏移、同名对象不串图、明确排除子控件、单节点失败后继续、陈旧窗口拒绝及资源释放；生产构建和 macOS arm64 打包通过。
- 连续压力采集中，系统批量截图接口也出现过超时；不将补采上限描述成全流程时限，不把缺失图片伪装成成功。没有宣称已支持 SurfaceView/OpenGL 独立表面、Compose/Flutter 内部绘制树，或所有 QML 复杂自绘。
- 已重启手机测试 App（未清数据）及最终打包版。最后只读检查时，桌面程序处于 3D 展开视图，显示 453 个节点，无补采失败横幅；可见独立的颜色面和图文块，选中的 `follow_bubble_container` 明确显示“结构容器，系统跳过自身绘制”。节点数量变化来自当前页面数据变化，不代表固定数量的性能对比。程序保持打开，未改动手机 App 代码，未提交或推送 GitHub。

窗口定位复用 [Android DDMS 的窗口查找方式](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/core/java/android/ddm/DdmHandleViewDebug.java)；调试暂停、方法调用与清理由 [JDWP 协议](https://docs.oracle.com/en/java/javase/22/docs/specs/jdwp/jdwp-protocol.html)约束。

## SurfaceView / OpenGL 独立表面支持

计划：

1. 不再用类名是否包含 `SurfaceView` / `TextureView` 判断类型。通过调试协议读取真实继承关系，识别 GLSurfaceView、播放器及自定义子类；纯容器仍不补造图片。
2. 沿用已确认窗口中的对象身份，读取控件自己的 Surface。优先复用系统同步像素拷贝；新系统改用本 App UID 下的独立缓冲层读取，不采集整个窗口，不混入邻居或父层。
3. 保护窗口/受保护内容不绕过限制。空 Surface、系统接口不可用、超时等可辨别失败明确说明；保留已有数量、像素、取消和资源释放限制。系统仅返回空结果时不猜测具体原因。
4. 位图进入现有 WebGL 和折叠合成通道。补协议测试，并使用当前手机的实际 SurfaceView 验证。

边界：OpenGL 输出可以作为所属 SurfaceView/GLSurfaceView/TextureView 的一张独立画面展示；不会把同一个 OpenGL 帧内的绘制指令伪装成原生子控件。动态视频和控件树依然不是同一帧的原子快照。

实现依据：[Android PixelCopy](https://developer.android.com/reference/android/view/PixelCopy)、[Android 14 ScreenCapture](https://android.googlesource.com/platform/frameworks/base/+/android-14.0.0_r1/core/java/android/window/ScreenCapture.java) 及 [SurfaceFlinger 的自身 UID 采集权限检查](https://android.googlesource.com/platform/frameworks/native/+/android-14.0.0_r1/services/surfaceflinger/SurfaceFlinger.cpp)。

### 实现与真机验证（2026-09-22）

- 已接入原生采集流程：按真实继承关系识别 SurfaceView / GLSurfaceView / TextureView 的自定义子类，优先读取独立缓冲。SurfaceView 的普通 DDMS 占位截图不再标记为成功采集的视频画面；尺寸发生变化则拒绝贴图。

- 修复静态页面补采等待超时：在安全的主线程消息边界设置断点后，通过不阻塞的只读显示列表请求唤醒消息队列；不在绘制过程中强行暂停，也不修改页面来触发刷新。
- 同一台 Android 14 真机的视频页面，两张自定义 TextureView 画面分别为 1273×2218、1251×2218，均读取成功；含层级查询的诊断约 6.4 秒，不是全页面采集耗时。

## 采集提速：第一轮（2026-09-26）

保留批量独立图层 + 按对象补采的现有链路，不降低图片分辨率，不删除控件树节点，不新增依赖。

- 大包接收不再反复拼接已收到的数据，分片数据只复制一次，降低内存拷贝和峰值占用。
- 先用轻量根节点查询确定窗口，只导出匹配窗口的完整属性。校验导出结束标记，残缺数据不进入图片采集；窗口身份仍严格匹配。
- 补采直接读取已定位对象的实际类型，按类型 ID 缓存继承关系，减少遍历应用类加载器。保留自定义 SurfaceView/TextureView 识别、视频优先、64 个补采/400 万像素/15 秒上限、安全窗口拒绝和资源清理。
- 进度拆分为完整属性、批量画面、特殊控件补采，便于区分慢在哪一步。

## 连续采集超时：第二轮（2026-09-26）

根因不是属性解析本身，而是自动补采阶段的旧 JDWP 路径。即使只发送 `VirtualMachine/IDSizes`，Android 14 真机上的目标进程后续也可能让 `ViewDebug.dumpViewHierarchy` 超时，最终返回没有 `DONE.` 的半截属性树。

- 自动补采改为只使用 DDMS `VUOP` 定点截图；不再在正常采集链路中发送 JDWP 类查找、断点、对象调用或 `Dispose`。
- 补采范围收紧为可见叶子控件，避免把父容器的合成画面再次贴到子层；原有批量图层仍优先使用，失败节点保留边框和错误原因。
- 真机连续两轮验证均成功：861 个节点、126 张独立画面，约 20 秒/轮；第二轮没有属性导出超时，日志没有新的 `DdmViewDebug` / `TimeoutException`。
- 103 项单元测试通过，生产构建通过。

限制：自动链路现在优先保证连续采集稳定性；受保护 Surface 或 OpenGL 外部缓冲仍可能只能得到 DDMS 可见结果或边框，不再用会污染下一轮调试状态的 JDWP 方式强行补采。
